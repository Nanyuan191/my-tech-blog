## 二、现场演示脚本

> 建议流程，控制在 **8-10 分钟**。每一步都先给结论再给证据。

### 第 1 步：证明真的在线（1 分钟）

**动作**：掏出手机，**关掉 WiFi 用 4G 流量**，打开 `http://<公网IP>:8080`。

**话术**：
> "这是主链接。我用手机流量而不是 WiFi，是为了排除只在内网可达的假象 —— 现在这个页面是从腾讯云的服务器上下载的。"

**加分点**：顺手打开 `/api/health`，指出 `database.ok: true`。
> "这个健康检查不只是返回一个 200，它真的对数据库执行了一次查询。进程活着不代表数据库连得上，我要确认整条链路是通的。"

### 第 2 步：展示前台功能（2 分钟）

**动作**：
1. 首页 → 展示文章卡片列表
2. 点进一篇文章 → **展示代码块语法高亮**
3. 点击某个标签 → 展示标签筛选
4. **在文章页按 F5 刷新** → 正常显示，不 404

**话术**：
> "文章是 Markdown 存储、前端渲染的。这里有三个库在协作：markdown-it 做格式转换，highlight.js 做代码高亮，DOMPurify 做 XSS 消毒。最后一层是必须的 —— Markdown 允许内嵌 HTML，不消毒就等于给作者开了一个注入后门。"

> "刚才我刷新了文章页没有 404，这其实是 Nginx 配置里一行 `try_files` 解决的。Vue Router 用 history 模式时 URL 是真实路径，刷新时浏览器真的去请求 `/posts/xxx`，服务器上没有这个文件就会 404。"

### 第 3 步：展示后台与鉴权（2 分钟）

**动作**：
1. 点登录 → 输入 admin 账号
2. 进后台 → 展示文章管理表格（能看到草稿状态的文章）
3. **新建一篇文章** → 填写标题、正文、选分类标签 → 发布
4. 回前台 → 新文章已经出现

**话术**：
> "后台用的是 JWT 双令牌方案。access token 活 2 小时放在前端内存里，refresh token 活 7 天存在 httpOnly Cookie 里 —— 后者 JavaScript 读不到，所以即使发生 XSS 也偷不走。"

### 第 4 步：证明鉴权真的生效（1 分钟）

**动作**：打开一个新的浏览器无痕窗口（不带任何 token），访问 `http://<公网IP>:8080/admin`。

**期望**：被重定向到登录页；或者直接用 curl 演示：

```bash
curl -i http://<公网IP>:8080/api/posts/admin
```

**期望输出**：`401` + `{"success":false,"message":"缺少访问令牌"}`

**话术**：
> "很多人做后台只是在前端隐藏了入口，接口其实还是裸奔的。我这里接口层面做了校验 —— 不带 token 直接请求后台接口会被 401 拒绝。"

### 第 5 步：演示 Docker 化的真实性（2 分钟）

**动作**：在服务器上（或本地）执行：

```bash
docker compose ps
```

展示三个容器 `Up`，其中 db 和 api 是 `(healthy)`。

```bash
docker compose down
docker compose up -d
```

展示"一条命令重新拉起全部服务"。

**话术**：
> "这是真的容器化，不是本地玩具 —— 线上就是跑在这套 compose 上的。三个服务有明确的依赖关系：db 有 healthcheck 做真实可用性探测，api 用 `condition: service_healthy` 等它就绪才启动。这个区别很关键，容器 running 不代表服务 ready。"

> "另外只有 web 服务暴露端口，api 和 db 都在内部网络里，这是最小暴露面原则 —— 数据库不碰公网。"

### 第 6 步：展示 CI/CD（1 分钟）

**动作**：GitHub → **Actions** 标签 → 点开最新一条流水线，展示三个 job 全绿。

**话术**：
> "推代码到 main 分支后自动触发：先做类型检查和 lint，通过后并行构建前后端两个镜像推到 GHCR，最后通过 SSH 部署到服务器。用 `needs` 串联是为了快速失败 —— 类型检查不通过就不会浪费资源去构建。"

## 三、预设问题与应答

### Q1：为什么不用 Next.js + Vercel？那个更流行吧？

**这个问题的核心不是"哪个更流行"，而是"哪个满足约束"。**

> "我评估过这个方案，但它有两条否决性问题。
>
> 第一，Vercel 是 Serverless 平台，**不运行 Dockerfile**。如果主站部署在 Vercel，那 `docker-compose.yml` 只能在本地跑，'一键拉起前后端及数据库'这句话就讲不通了 —— 这直接损失 Docker 化这个加分项。
>
> 第二，`*.vercel.app` 域名在国内 DNS 解析不稳定，而'公网可访问'是必须项，不能赌。
>
> 所以选了自持服务器 + 容器编排的路线。开发体验上确实比 Vercel 麻烦，但换来了对整条链路的完全掌控。"

### Q2：Express 性能不如 Fastify，为什么不用 Fastify？

**关键是：在这个场景下性能不是瓶颈。**

> "Fastify 的基准 QPS 确实比 Express 高两三倍。但这是个人博客，实际峰值 QPS 可能不到 10 —— 瓶颈根本不在 Web 框架，而在数据库查询和网络 IO。换 Fastify 带来的提升用户感知不到。
>
> 我选 Express 是因为它的中间件模型最直观，我能指着代码讲清请求怎么流过每一层。如果要讲的是性能优化，那选型结论会不一样。"

### Q3：Prisma 生成的 SQL 不是最优的，为什么用 ORM？

**承认局限，说明补位。**

> "这个批评是对的，ORM 生成的 SQL 确实可能不是最优。所以我在关键路径上做了主动优化：
>
> 一是列表查询用 `select` 精确控制字段，不把正文那个几十 KB 的大文本查出来；
> 二是在 schema 里给 `[status, publishedAt]` 加了复合索引，因为这是列表页最常用的查询条件；
> 三是浏览量自增用 `increment` 而不是先读后写，避免并发下的丢失更新。
>
> 如果真到了 ORM 表达不了的复杂查询，Prisma 也支持 `$queryRaw` 手写 SQL 兜底。"

### Q4：Markdown 渲染为什么需要 DOMPurify？不是自己的后台吗？

**这是信任边界的问题。**

> "因为 Markdown 规范允许内嵌原始 HTML。就算只有一个管理员，也存在两个风险：
>
> 一是账号被盗的情况 —— 攻击者发一篇恶意文章，所有访客的 token 都会被偷走；
> 二是以后如果开放评论或者多人协作，恶意内容就不再是可控的。
>
> 加一层 DOMPurify 的成本几乎是零，但它把'作者内容'和'访客浏览器'之间的信任边界划清了。这是纵深防御的思路。"

### Q5：容器里为什么不用 root？有什么实际影响？

> "容器逃逸类漏洞的前提通常是'容器内进程是 root'。比如经典的 CVE-2019-5736，就是通过覆盖宿主机上的 runc 二进制来逃逸的，需要容器内有 root 权限才能写入。
>
> 用普通用户跑，即使应用被攻破，攻击者拿到的也只是容器内的低权限账号，横向移动到宿主机或者其他容器的难度大幅提高。
>
> 代价只是在 Dockerfile 里加两行 `adduser` 和 `USER`，没有理由不做。"

### Q6：为什么密码错误和用户不存在返回同样的消息？

**这是防用户名枚举。**

> "如果分别返回'用户不存在'和'密码错误'，攻击者就能通过错误信息的差异枚举出系统里有哪些用户名是真实存在的。拿到有效用户名列表后，暴力破解的难度就下降了一个数量级。
>
> 更进一步，我还处理了时序攻击。如果用户不存在就直接返回，响应会比密码错误快 100 毫秒左右 —— 因为少了 bcrypt 计算。攻击者统计响应时间也能推断出用户名是否存在。所以我在用户不存在时也执行一次假的 bcrypt 比较，把时间差抹平。"

### Q7：access token 为什么不存在 localStorage？

> "因为 localStorage 能被 JavaScript 读取。一旦发生 XSS，攻击者可以一行代码把 token 发到自己的服务器上。
>
> 我把 access token 存在前端的内存变量里，刷新页面就没了（由 refresh 流程恢复）。而 refresh token 放在 httpOnly Cookie 里，JavaScript 根本读不到。
>
> 这样两个令牌都不在 XSS 能触及的范围内。"

### Q8：如果服务器挂了怎么办？

**这个问题要展示有预案，而不是"不会挂"。**

> "三个层面的应对：
>
> 一是容器层面，所有服务都配了 `restart: unless-stopped`，进程崩溃会被自动拉起。加上 healthcheck，卡死的情况也能被检测到。
>
> 二是数据层面，MySQL 数据存在 Docker 命名卷里，容器重建不会丢数据。需要的话可以再加定时备份。
>
> 三是入口层面，我准备了 GitHub Pages 的静态快照作为备份演示链接。如果服务器出状况，至少还有一个能打开的地址。"

### Q9：备案没通过怎么办？

**这是必须项1 的保险问题，必须答得笃定。**

> "主链接用的是 `http://<公网IP>:8080`。ICP 备案只约束 80 和 443 端口，非标准端口不受限制 —— 所以这个链接在服务器开通当天就能用，完全不依赖备案进度。
>
> 备案我同步在走流程。通过之后，只需要把 compose 里的端口映射从 8080 改成 80，再配一下 HTTPS，就平滑切换成域名访问。交付期和长期方案是解耦的，不会因为备案卡住而影响交付。"

### Q10：这个项目里你觉得最难的技术点是什么？

**挑一个能体现工程判断的，不要挑"参数最复杂"的。**

> "是 Docker Compose 的启动顺序问题。
>
> 表面上看，`depends_on` 写上去就完事了。但实际跑起来会发现：三个容器状态都是 Up，后端日志里却全是连接数据库失败。
>
> 原因是 `depends_on` 默认只等容器**启动**，而 MySQL 容器启动后还要初始化数据目录、建系统表，这期间端口是通的但连接会被拒绝。后端启动得比它快，连不上就退出了。
>
> 解法是用 `healthcheck` 做真实可用性探测，再用 `condition: service_healthy` 等它真正就绪。
>
> 这个坑让我理解了一个更普遍的道理：**'进程起来了'和'服务可用了'是两件完全不同的事**。这个认知在后来做优雅退出、健康检查这些地方都用上了。"
