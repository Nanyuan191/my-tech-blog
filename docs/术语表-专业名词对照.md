## 一、Docker 相关（最容易混的一组）

### 镜像（Image）

**一句话**：一个"只读的软件安装包"，里面装好了操作系统、运行环境、你的代码，随时可以启动成一台小电脑。

**类比**：**游戏光盘 / 系统装机 U 盘**。光盘本身是死的，不能"运行游戏"，但你可以用它装出一台能跑游戏的电脑，装多少台都行。

**本项目里的体现**：
- `blog-system-api:latest` —— 788 MB，里面是 Node 环境 + 编译好的后端代码 + 生产依赖
- `blog-system-web:latest` —— 76 MB，里面是 Nginx + 编译好的前端静态文件（HTML/CSS/JS）

> 我上一轮说的"**前端镜像**就是指 `blog-system-web` 这个镜像"。之所以要提它，是因为**装修改完前端样式后，必须重新构建这个镜像**，否则 8080 上跑的还是老样子——镜像只是"安装包"，你不重新打包，它不会自己变。

### 容器（Container）

**一句话**：镜像**运行起来**的那个实例。

**类比**：镜像 = 光盘，容器 = 用这张光盘装出来的那台电脑。同一张光盘可以装出很多台电脑（多个容器），它们互不干扰。

**本项目里的体现**：`blog-web` / `blog-api` / `blog-db` 三个容器，分别由三个镜像启动。

**镜像 vs 容器的区别**（高频混淆点）：

| | 镜像 | 容器 |
|---|---|---|
| 状态 | 静态文件，躺着不动 | 正在运行的进程 |
| 能不能改 | 不改（改了就产生新镜像） | 能改，但重启就没了 |
| 数量关系 | 一个镜像 → 可以起 N 个容器 | 一个容器 → 来自某一个镜像 |
| 命令 | `docker images` | `docker ps` |

### Dockerfile

**一句话**：构建镜像的**配方文件**，一行行写清楚"先装什么、再拷什么、最后怎么启动"。

**类比**：菜谱。照着菜谱做出菜（镜像），同一张菜谱做多少次味道都一样。

**本项目里的体现**：`apps/api/Dockerfile`、`apps/web/Dockerfile`。用的是**多阶段构建**——先在一个大阶段里装依赖、编译代码，再把"编译结果"单独拷到一个干净的小阶段里。这样最终镜像里没有源代码、没有开发依赖，体积小很多。

### 多阶段构建（Multi-stage build）

**一句话**：一个 Dockerfile 里写多个 `FROM`，前面的阶段当"施工队"，最后一个阶段当"交付的房子"。

**类比**：装修时搭建的脚手架，装修完是要拆掉的，最后住进去的人看不到脚手架。

**本项目里的体现**：后端 Dockerfile 有三个阶段 —— `deps`（装依赖）→ `builder`（编译 TS + 生成 Prisma Client）→ `runner`（只留编译产物 + 生产依赖）。

### 构建上下文（Build context）

**一句话**：`docker build` 时，Docker 会先把指定目录里的文件**全部打包**发给构建引擎，这一包东西就是构建上下文。

**类比**：寄快递时你往箱子里塞的所有东西。塞得越多，运费越贵、时间越长。

**本项目里的体现**：一开始没写 `.dockerignore`，整个 `node_modules`（几千个文件、几百 MB）被打包送进去了。加上 `.dockerignore` 后，构建上下文从**数百 MB 降到 263 KB**。

### 镜像分层与缓存

**一句话**：Dockerfile 里每条指令生成"一层"，只要某层的内容没变，下次构建直接复用，不重新执行。

**类比**：做菜时的半成品。已经切好的菜、熬好的高汤，下次直接拿来用。

**本项目里的体现**：Dockerfile 里先 `COPY package.json` 再 `COPY 源码`——这样你只改业务代码时，"装依赖"那一层命中缓存，构建从几分钟降到几秒。

### Docker Compose

**一句话**：用一个 YAML 文件描述"要起哪几个容器、它们怎么互相连接"，然后一条命令全拉起来。

**类比**：乐队的乐谱。每个乐手（容器）各弹各的，但乐谱规定了谁先起、谁配合谁。

**本项目里的体现**：`docker-compose.yml` 定义了 web / api / db 三个服务，一条 `docker compose up -d` 全部拉起。

### 编排（Orchestration）

**一句话**：管理多个容器的启动顺序、依赖关系、网络、健康状态。Compose 是最轻量的编排工具。

### 数据卷 / 命名卷（Volume）

**一句话**：一块**不受容器生命周期影响**的存储空间。容器删了，卷里的数据还在。

**类比**：容器是租的房子，卷是你自己的保险柜。退租了，保险柜里的东西还在。

**本项目里的体现**：`blog-system_db_data` 这个命名卷存着 MySQL 的所有数据文件。**所以你关电脑、重启、甚至删容器，文章数据都不会丢**——只要不执行 `docker compose down -v`（`-v` 就是连卷一起删）。

### 健康检查（Healthcheck）

**一句话**：让 Docker 定期"探一下"容器里的服务是不是真的能用，而不只是"进程还在"。

**类比**：看店员在不在岗（进程活着）≠ 店能不能正常营业（服务可用）。MySQL 启动后要 10-30 秒才真正能接受连接。

**本项目里的体现**：`depends_on: condition: service_healthy` —— api 会一直等 db 的 healthcheck 通过才启动。这是"容器都 Up 但后端一直报连接数据库失败"的根治办法。

### registry（镜像仓库）

**一句话**：存放镜像的"网盘"。Docker Hub 是最有名的公共仓库，GHCR 是 GitHub 提供的。

**类比**：App Store。你构建好镜像推上去，服务器上拉下来就能跑。

## 二、网络与域名

### 反向代理（Reverse proxy）

**一句话**：所有请求先到它这里，它再决定转给后面哪个服务。

**类比**：公司前台。访客不直接找员工，前台按你来意分派。

**本项目里的体现**：Nginx 收到请求，`/api/*` 转给后端容器，其他路径返回前端页面。好处是前端后端对浏览器来说**同一个域名**，天然没有跨域问题。

### 端口（Port）

**一句话**：一台机器上不同服务的"门牌号"。

**本项目里的体现**：`8080:80` 意思是"把宿主机的 8080 端口，接到容器里的 80 端口"。

⚠️ **只映射必要的端口**：本项目只映射了 web 的 8080。api 和 db 都不对外暴露——这叫**最小暴露面原则**。如果给 MySQL 映射 3306，等于把数据库直接摆到公网上。

### CORS（跨域资源共享）

**一句话**：浏览器的安全机制——默认禁止一个网站去请求另一个域名的接口，除非对方明确"允许"。

**本项目里的体现**：开发时前端跑在 `5173`、后端跑在 `3000`，属于跨域，所以后端开了 CORS 只允许 5173。**生产环境前后端同域（都走 Nginx），不存在跨域，所以生产环境直接关掉 CORS**。

### SPA 与 history 模式

**一句话**：单页应用。整个网站只有一个真实的 HTML 文件，页面切换是 JS 在换内容，不真的跳转。

**坑在哪**：`/posts/xxx` 这种地址直接按 F5 刷新时，浏览器真的去服务器要这个文件，而服务器上没有 → 404。

**本项目解法**：Nginx 里写 `try_files $uri $uri/ /index.html` —— 找不到文件就返回 index.html，交给前端路由自己解析。

### ICP 备案

**一句话**：中国大陆的服务器 + 域名 + 80/443 端口提供网站服务，需要向工信部备案（约 3-20 工作日）。

**规避办法**：用 `http://IP:8080` 这种"IP + 非标准端口"的形式可以直接访问，跳过备案。这也是我们主链接用 8080 的原因。

### 代理（Proxy）与两种模式：规则模式 / 全局模式

**一句话**：代理软件把你的一部分网络请求"绕道"送到境外服务器再转发出去，从而访问被限制的网站。

**两种模式天差地别**：

| 模式 | 行为 | 什么时候用 |
|---|---|---|
| **规则模式 / PAC / 分流** | 按一份名单判断：国内网站直连、名单内的才走代理 | 日常上网（国内网站更快） |
| **全局模式** | **所有**流量一律走代理 | 某个网站打不开时，先用它排除"名单漏了这个网站"的可能 |

**类比**：规则模式像"只有出境航班才走专用通道"，全局模式是"所有航班都走专用通道"。

**本项目里的踩坑现场**：GitHub 域名没被规则命中时，请求走了**直连**，于是被对方当成国内 IP 处理 → 直接返回 403。**打不开 GitHub 时，第一个动作就是切"全局模式"，能解决相当一部分情况。**

> **自查出口 IP 的方法**（⚠️ ipinfo.io 现在要登录才能看，别用它，实测 2026-10-01）：
> - **最简单**：百度搜索「**IP**」，搜索结果第一条卡片直接显示"本机IP … 归属地：某国某城"
> - **备选**：浏览器打开 `https://ip.3322.net`（只给一串 IP 数字，把数字粘到百度搜一下也能查归属地）
> - **最直接**：看你代理软件面板上当前选中的节点（一般写着 香港 / 日本 / 美国 等）
>
> 判断标准：**百度显示的归属地是国内 → 代理没生效（或这个网站漏了分流），切全局模式**；显示境外 → 出口没问题，换"换节点 / 换无痕窗口 / 等一会儿"这三招

### DNS（域名系统）

**一句话**：把"网址"翻译成"IP 地址"的**电话簿**。你输入 `github.com`，DNS 告诉你它对应 `140.82.116.3`。

**类比**：要给朋友打电话，你只记得名字（域名），得先查通讯录拿到号码（IP）才能拨出去。DNS 就是这本通讯录。

**本项目里的体现**：浏览器访问你的网站时也是先查 DNS 拿到腾讯云服务器的 IP，才连得上。**DNS 这一步出问题，后面全部打不开**——而且症状看起来像"网站挂了"，其实网站好好的。

### DNS 污染（DNS poisoning / 投毒）

**一句话**：你查通讯录的时候，有人**故意给了你一个错的号码**。

**本项目实测铁证（2026-10-01）**：本机 DNS 是路由器地址 `192.168.1.1`，查 `www.google.com` 返回 **`31.13.92.37`** —— 那是 **Facebook 的 IP**。域名被指向了完全不相干的服务器。

**为什么"时好时坏"**：污染是**间歇性**的（有时给对、有时给错），所以表现就是"有的站能开、有的开不了、刷新几次又好了"。**你这两天遇到的怪现象，根源就是它。**

**怎么治**：让域名解析也走代理 → 在代理软件里开 **TUN 模式** + **远程 DNS / DoH**（见下面两条）。

### DNS 泄漏（DNS leak）

**一句话**：代理只接管了"网页请求"，**没接管"域名解析"**——解析请求还是从本地网络（路由器 / 运营商）发出去的。

**类比**：包裹走了专用通道（代理），但**问路时却问了街边随便一个人**（本地 DNS）。路问错了，包裹自然到不了。

**后果**：域名解析走的还是那条会被污染的通道，等于**白代理了**。

**自查**：换个节点 / 开远程 DNS 之后，"时好时坏"消失了 → 说明之前就是 DNS 泄漏。

### 远程 DNS / DNS over HTTPS（DoH）

**一句话**：把"查域名"这件事也**加密**后交给代理远端去查，本地网络既看不到你查了什么，也没法篡改答案。

**类比**：不在街边问路，改成**给交警指挥中心打加密电话问路**——没人能中途塞假消息给你。

**哪里开**：多数代理客户端在设置里有"远程 DNS""DNS 设置""DoH"这类开关，打开即可。

### TUN 模式（虚拟网卡模式）

**一句话**：在系统里虚拟出一块网卡，把**所有流量**（不只是浏览器的网页请求）都接管走代理——包括 DNS 解析、命令行工具、游戏。

| | 系统代理 | TUN 模式 |
|---|---|---|
| 接管范围 | 只接管"遵守代理设置"的程序（浏览器、多数软件） | **全部流量**，含 DNS、命令行、游戏 |
| 需要管理员权限吗 | 不需要 | **需要**（要装虚拟网卡驱动） |
| 能治 DNS 污染吗 | 不一定 | **能**——因为解析请求也走代理了 |

**本项目里的体检结论**：实测发现你的代理**已经是 TUN / 全局模式**（连工具自己的直连请求都从中国香港出去了）——所以**你的代理本身是好的**，问题出在**节点（香港）被 GitHub 限流**。详见第七节。

### TLS（传输层安全）

**一句话**：HTTPS 里那个 "S"，是你和网站之间的一条**加密隧道**。

**怎么用**：浏览器先跟服务器握手（交换证书、协商密钥），隧道建好之后才传数据。

**关键区分**：**TCP 通（端口能连上）≠ TLS 通（隧道能建成）**。两个是不同层面的检查。

**本项目里的体检结论**：实测 `github.com` 的 **TCP 443 能连通**，但 HTTPS 请求**超时** —— 端口通、握手被掐断。这是**"代理节点被限流"**的典型特征，不是"没连上"。

### 403 Forbidden（禁止访问）

**一句话**：HTTP 状态码之一。**401 是"你没登录"，403 是"我知道你是谁，但就是不让你进"。**

**本项目里的体现**：你后端自己也在用这几个码，而且用得很讲究：
- **401** → 未登录却访问了后台接口
- **403** → 已登录但角色不够（比如普通编辑去改别人的文章）
- **404** → 匿名访问草稿。⚠️ **这里故意用 404 而不是 403** —— 因为 403 等于变相承认"这篇文章确实存在"，404 才是"查无此文"

### 人机验证（CAPTCHA）

**一句话**：让你勾一下"我不是机器人"或点几张图，用来区分真人和程序。

**为什么对你弹**：网站发现你这个出口 IP 的行为"像机器人"（同一 IP 上短时间请求过多、或这个 IP 被很多人共用）就会弹验证。**这不是封号，只是怀疑。**

**为什么验证框加载不出来（你遇到的正是这个）**：验证组件本身也是**境外资源**，网络不通时它加载不出来 → 于是变成"页面出来了，但根本没有地方给你点"。**症状是"找不到验证框"，病根是"没真正连上"。**

### 风控与 IP 信誉

**一句话**：网站给每个出口 IP 默记的一个"信用分"。IP 被很多人共用（公共代理节点、机房 IP）时，信誉就低。

**本项目里的体现**：你的接口也有同类防线——`express-rate-limit` 限制同一 IP 的请求频率，防止有人写脚本暴力猜管理员密码。

## 三、前端相关（为什么说它"静态又不静态"）

### 静态资源（Static assets）

**一句话**：不需要程序现场生成、服务器直接把文件读出来返回给浏览器的东西——HTML、CSS、JS、图片都算。

**类比**：自动售货机。你按按钮（访问网址），它把现成的饮料递出来，**不现场调制**。

**本项目里的体现**：前端构建产物放在 web 镜像的 `/usr/share/nginx/html/` 里，只有 **1 个 index.html（759 字节）+ 13 个 assets 文件（JS/CSS）**。Nginx 的活儿就是"你要哪个文件我递哪个"，它不会去数据库取文章。

### 构建产物 / dist（Bundle）

**一句话**：源代码经过打包、压缩、转译之后，真正拿去部署的那堆文件。

**类比**：面粉（源码）→ 面包（构建产物）。服务器上只放面包，不放面粉和烤箱。

**本项目里的体现**：`npm run build` 之后生成的 `apps/web/dist/`。Dockerfile 里 `builder` 阶段负责烤面包，`runner` 阶段只把面包拷进 Nginx 镜像——所以 web 镜像只有 76MB（**里面没有 Node、没有源代码**）。

### SPA（单页应用）

**一句话**：整个网站**只有一个真实的 HTML 文件**。所谓"页面切换"，其实是 JS 把内容换掉，浏览器并没有真的跳转。

**类比**：话剧舞台。换幕换景是工作人员在幕后搬道具，观众（浏览器）没换场地。

**本项目里的体现**：`/`、`/posts/xxx`、`/login`、`/admin` 四个页面，Nginx 统统返回那同一个 `index.html`（靠 `try_files ... /index.html` 兜底），是 Vue Router 在浏览器里决定渲染哪一个。

### CSR（客户端渲染）—— 本项目采用的方式

**一句话**：页面内容由**浏览器里的 JS 运行起来之后**才生成。

**类比**：宜家家具。商家寄给你一堆零件和图纸（JS），你在家自己装（浏览器渲染）。寄的时候箱子里没有成品。

**本项目里的体现（可自己验证）**：
- 浏览器打开 `http://localhost:8080`，**右键 → 查看网页源代码** → 看到的是 `<div id="app"></div>` 空壳，**一个文章标题都没有**
- 按 **F12 → Elements** 看 → 文章标题、分类、标签全都在
- 两条路看到的不一样，就证明内容是 JS 运行时塞进去的

### SSR / SSG（服务端渲染 / 静态生成）—— 对比项

| | CSR（本项目） | SSR | SSG |
|---|---|---|---|
| 内容在哪生成 | 浏览器（JS 跑起来后） | 服务器（每次请求） | 构建时（一次性） |
| 服务器上的 HTML | 空壳 | 完整内容 | 完整内容 |
| SEO 效果 | 较弱 | 好 | 最好 |
| 典型代表 | Vue SPA / React SPA | Nuxt / Next.js | VitePress / Astro |

**为什么本项目选 CSR**：博客只有一个作者、不需要被搜索引擎大力收录，而 CSR 换来的是**前后端彻底分离**——前端只管展示，后端只管数据和接口。这正好是考核要考的"全栈基础"，链路最清楚。

### SEO（搜索引擎优化）

**一句话**：让你的网页在百度/Google 搜索结果里排得更靠前的各种做法。纯 CSR 的站点在这方面天然吃亏，因为爬虫拿到的 HTML 是空壳。

**答辩怎么答**：如果被问"你这站 SEO 怎么样"，正解是承认取舍——"纯 SPA 的 SEO 较弱，如果要做可以上预渲染或 SSR，但本项目的考核重点是前后端分离与工程交付，所以我优先保证了架构清晰"。**主动说出取舍，比硬撑加分。**

### 代码分割 / 分块（Code splitting / chunk）

**一句话**：把一个大 JS 文件拆成多个，用户打开哪个页面才下载哪个。

**本项目里的体现**：`assets/` 目录里能看到 `HomeView-xxx.js`、`PostView-xxx.js`、`LoginView-xxx.js`、`AdminView-xxx.js` —— 每个页面各自一个文件。首页访客不会被迫下载后台管理那 57KB 的 CSS。

## 四、后端与数据库

### 中间件（Middleware）

**一句话**：请求在到达业务代码前，必须依次经过的一道道"关卡"。

**类比**：机场安检流程——值机 → 安检 → 登机口，每一步都能拦下你。

**本项目里的体现**：`helmet`（加安全头）→ `cors` → `compression` → `json 解析` → `cookieParser` → `morgan`（记日志）→ 路由 → 404 → 错误处理。

### 控制器（Controller）

**一句话**：请求进来后的"接待员"——只做三件事：核对点单（校验参数）、喊厨房做菜（调服务层）、把菜摆盘端出去（组装响应 JSON）。

**类比**：餐厅服务员。他不进厨房做菜，也不管仓库进货；他只负责确认"你点的是什么、有没有点错"，然后把菜单递给厨房，最后把做好的菜端给你。

**本项目里的体现**：`article.controller.ts`。你在后台发文时，它先检查"标题不能为空、密码至少 6 位"，检查通过才把数据交给服务层；你传的参数不合法，返回 400 的也是它。

### 服务层（Service）

**一句话**：真正"干活"的地方——业务规则全在这里，只有它有权读写数据库。

**类比**：餐厅后厨厨师。服务员说"一份微辣的番茄炒蛋"，**怎么炒、放多少盐、先炒蛋还是先炒番茄**，都是厨师的事。

**为什么要分两层（答辩会问）**：同一个业务规则可能被多个入口调用（网页接口、定时任务、未来的小程序接口）。规则写在 Service 里，改一次、到处生效；如果写在 Controller 里，就得每个入口抄一遍，漏一处就是 bug。

**本项目里的体现**：`article.service.ts`（263 行，全项目最大）。"草稿只有管理员能看"、"浏览量用原子自增防止并发丢失"、"摘要没填就自动截正文前 150 字"——这些规则全在这一层。

### 路由层（Route）——把上面几层串起来

**一句话**：一张"网址 → 处理函数"的对照表，外加进门前的安检安排。

**类比**：餐厅的**领位员 + 门禁**。你进门说"我找 3 号桌"，他把你领到对应的位置；VIP 包间（后台接口）他还会先看你的会员卡（requireAuth 鉴权）。

**本项目里的体现**：`routes/article.ts`。`GET /api/posts` 指给 `articleController.list`；写操作（POST/PUT/DELETE）必须先过 `requireAuth` 这道安检；还有个著名的坑——`/:slug` 这种通配路径必须注册在 `/stats` 这种固定路径**之后**，否则"站点统计"会被当成"查一篇叫 stats 的文章"。

> **一次请求的顺序**：路由层（领位）→ 控制器（服务员）→ 服务层（厨师）→ Prisma（传菜员兼翻译）→ 数据库（仓库）。菜做好后原路端回来。

### Prisma

**一句话**：一个 ORM（对象关系映射）工具，让你用 JavaScript 对象操作数据库，不用手写 SQL 语句。

**类比**：**会说两种语言的传菜员**。你对他说中文（`prisma.article.findMany(...)`），他跟仓库用 SQL 对暗号（`SELECT * FROM articles WHERE ...`），你完全不用学 SQL 方言。

**它由三部分组成**（对应你项目里的三个东西）：

| 组成 | 是什么 | 在你项目里 |
|---|---|---|
| **Schema**（模型定义） | 一份文件写清"数据库有哪些表、表里有哪些列、表之间什么关系" | `apps/api/prisma/schema.prisma`（6 张表全在这） |
| **Migration**（迁移） | 根据模型变化自动生成 SQL，负责真正改表结构 | `prisma/migrations/` 目录 |
| **Prisma Client**（客户端） | 根据模型自动生成的带类型提示的查询代码 | `node_modules/.prisma`，业务代码里 `import { prisma } from '../lib/prisma'` 用的就是它 |

**为什么选它而不手写 SQL（答辩标准答法）**：
1. **类型安全**——字段名写错，编译器当场标红，而不是上线后查半天 undefined
2. **防 SQL 注入**——所有查询自动参数化，用户输入永远不会被拼进 SQL 语句
3. **迁移有版本记录**——数据库结构怎么变的，每次都存档在 Git 里，可回滚

**本项目里的体现**：全文搜 `prisma.article` 能看到所有数据库操作：`findMany`（查列表）、`findUnique`（查单篇）、`create`（新增）、`update`（更新）、`delete`（删除）、`count`（计数）、`aggregate`（求和，统计总浏览量用的）。

### ORM

**一句话**：Object-Relational Mapping，"用操作对象的方式操作数据库"这类工具的**统称**，不手写 SQL。

**类比**：翻译官。你说中文（JS 对象），他帮你翻成 SQL 跟数据库谈。

**本项目里的体现**：我们项目用的 ORM 就是 **Prisma**（详见上一条）。

### 数据库迁移（Migration）

**一句话**：把"表结构的变化"记录成一个个带版本号的 SQL 文件，可以按序执行、可以回滚。

**类比**：Git 之于代码 = Migration 之于数据库结构。

**本项目里的体现**：`prisma/migrations/20260930091014_init/migration.sql` 就是第一个迁移文件。用 `migrate dev`（开发，会自动改表）或 `migrate deploy`（生产，只执行已有迁移，不擅自改）。

### 种子数据（Seed）

**一句话**：把"空数据库"填成"能演示的样子"的脚本。

**本项目里的体现**：`prisma/seed.ts` 灌入 admin 账号 + 3 分类 + 8 标签 + 3 篇文章。答辩时打开后台不至于一片空白。

### 事务（Transaction）

**一句话**：一组操作"要么全成功，要么全失败"，不允许做一半。

**类比**：转账。扣了你的钱却没加到对方账上，是不能接受的。

**本项目里的体现**：文章列表查询用 `prisma.$transaction([查总数, 查数据])` —— 保证两条查询看到的是同一时刻的数据，否则可能在两次查询之间有人刚插了一篇文章，导致"总数说有 25 篇，页面上只显示 24 篇"。

### 索引（Index）

**一句话**：给数据库表加的"目录"，让查询不用一行行翻。

**本项目里的体现**：`@@index([status, publishedAt])`。首页查询是"筛已发布 + 按时间倒序"，正好命中这个索引。

### 幂等（Idempotent）

**一句话**：同样的操作执行一次和执行十次，结果一样。

**本项目里的体现**：种子脚本用 `upsert`（存在就更新、不存在就创建）而不是 `create`。所以你手滑多跑几次不会报错、不会产生重复数据。

### slug

**一句话**：URL 里用来标识一篇文章的"短名字"，比数字 ID 好看也好记。

**本项目里的体现**：`/posts/why-vue-express-over-nextjs`。中文标题没法直接做 slug（URL 里会变成一串 `%E4%B8%BA` 之类的编码），所以策略是"保留英文数字，中文用 `post-随机串` 兜底"。

### RBAC

**一句话**：Role-Based Access Control，基于角色的权限控制——不是"给每个人单独配权限"，而是"给角色配权限，再把人放进角色"。

**本项目里的体现**：`users` 表有 `role` 字段（ADMIN/EDITOR），`requireRole()` 中间件负责校验。

### 声明合并（Declaration merging）

**一句话**：TypeScript 允许你"往已有类型上追加字段"。我们用它给 Express 的 `Request` 类型加了一个 `user` 字段。

**为什么需要**：否则你在 controller 里写 `req.user` 会报"该属性不存在"。

## 四、认证与安全

### 令牌 / Token

**一句话**：登录成功后服务器发给你的一张"通行证"，后续请求带着它证明"我是谁"。

### JWT（JSON Web Token）

**一句话**：一种令牌格式，内容用 Base64 编码 + 服务器私钥签名。**看得见内容，但改不了**（改了签名就对不上）。

**注意**：因为内容可见（不含密码，只有用户 id、用户名、角色），**不要把敏感信息塞进 JWT**。

### access token / refresh token（双令牌）

| | accessToken | refreshToken |
|---|---|---|
| 有效期 | 2 小时 | 7 天 |
| 干什么 | 每次业务请求都带 | 只用来换新的 accessToken |
| 存哪 | 前端内存 | httpOnly Cookie |

**为什么两个**：一个长期令牌泄漏 = 永久失守。拆开后业务请求用短命的那个，泄漏窗口被压到 2 小时。

### 哈希（Hash）

**一句话**：单向转换——从原文能算出哈希，从哈希**算不回**原文。

**本项目里的体现**：密码只存哈希。数据库被人偷走了，也还原不出原密码。

### 加盐（Salt）

**一句话**：哈希之前给密码掺一段随机字符串。

**为什么**：不加盐的话，密码 `123456` 的哈希永远一样，攻击者拿一张"常见密码哈希表"（彩虹表）批量对着查就能破。加盐后同一个密码每次哈希结果都不同。

### 暴力破解与 cost

**一句话**：cost 是 bcrypt 的"计算难度旋钮"。cost=10 时算一次约 100ms，正常登录无感，但暴力破解的成本被放大 1024 倍。

### XSS（跨站脚本攻击）

**一句话**：攻击者把恶意 JS 代码混进你的网页内容里，别人打开页面时这段代码就在别人浏览器里执行了。

**本项目里的体现**：博客允许发 Markdown，Markdown 可以写 HTML → 风险点。**解法**：前端用 DOMPurify 清洗渲染结果，把危险标签和属性删掉再插入页面。

### CSRF（跨站请求伪造）

**一句话**：诱导你（已登录的用户）在不知情的情况下，用你的身份去发请求。

**本项目里的体现**：refreshToken 的 Cookie 设置了 `sameSite=lax`，阻止跨站请求携带它。

### 越权访问

**一句话**：本不该看到/操作的内容，被看到了/操作了。

**本项目里的体现**：草稿只有管理员能看。非发布状态的文章，无论匿名还是普通用户访问，统一返回 **404** 而不是 403 —— 因为 403 等于承认"这篇文章存在"。

### httpOnly

**一句话**：Cookie 上的一个标记，意思是"禁止 JavaScript 读取它"。

**作用**：即使网站被 XSS 攻破，攻击者写的 JS 也偷不走这个 Cookie。

### OAuth（第三方登录）

**一句话**：用一个网站的账号登录另一个网站——比如"用 GitHub 登录 ipinfo"、"用微信登录某 App"，你不用在新网站再注册一套账号密码。

**类比**：酒店前台复印你的身份证登记入住，而不是把身份证原件交给酒店。

**怎么认出它**：页面标题通常是「Sign in to GitHub **to continue to** 某网站」——意思是"GitHub 只是来验证你身份的，验完回到那个网站去"。⚠️ **这种页面只管登录，不管注册新 GitHub 账号**；注册必须直接去 `github.com/signup`。

**本项目里的体现**：你后端的 JWT 就是同一思想——登录成功后发一张令牌，别的接口认令牌不认密码。

## 五、工程与流程

### monorepo

**一句话**：一个代码仓库里放多个项目（前端 + 后端），共享依赖和配置。

**对比**：polyrepo（前后端各一个仓库，互相不知道对方存在）。

**本项目里的体现**：`blog-system/` 下 `apps/web`（前端）+ `apps/api`（后端）。

### npm workspaces

**一句话**：npm 官方支持的 monorepo 方案，让多个子包共用一份 `node_modules`。

**本项目里的体现**：在根 `package.json` 里声明 workspaces，依赖会**提升到根目录**。⚠️ 这带来一个真实踩过的坑：子目录 `apps/api/node_modules` **根本不存在**，Dockerfile 里写 `COPY apps/api/node_modules` 会直接报错。

### CI / CD

- **CI（持续集成）**：每次推代码，自动跑一遍检查（类型检查、构建、测试）。目的是"尽早发现坏味道"。
- **CD（持续部署）**：检查通过后，自动构建镜像、推送到仓库、部署到服务器。

**本项目里的体现**：`.github/workflows/ci-cd.yml`（180 行）。效果是——你改完代码 `git push`，GitHub 自动构建新镜像并推到 GHCR，服务器上一条命令就能更新。

### 流水线（Pipeline）

**一句话**：CI/CD 的完整执行流程，由一系列"步骤"组成。

### GHCR

**一句话**：GitHub Container Registry，GitHub 提供的镜像仓库。

### 仓库（Repository）

**一句话**：GitHub 上存放代码的地方。

⚠️ **注意"仓库"这个词有两个用法，别混**：
1. **代码仓库**（Git repository）= GitHub 上存你代码的地方
2. **镜像仓库**（Image registry）= 存 Docker 镜像的地方（Docker Hub / GHCR）

你问的"GitHub 不是仓库吗，有 Docker Desktop 不够吗"——答案是：**这两个仓库装的东西不一样，一个装代码，一个装镜像，互相替代不了**。详见下面第六节。

### Commit / Push / Pull

| 操作 | 一句话 |
|---|---|
| commit | 把改动"存档"一次，带一句说明 |
| push | 把本地的存档**上传**到远程仓库（GitHub） |
| pull | 把远程的改动**下载**到本地 |

## 六、Docker Desktop、GitHub、云服务器到底什么关系

这是你问得最实在的一个问题，单独讲清楚。

### 它们解决的是两个完全不同的问题

| | Docker Desktop | GitHub |
|---|---|---|
| 干什么 | **在你电脑上**构建和运行容器 | **在云端**存放和协作代码 |
| 装的是 | 镜像（可运行的程序包） | 代码文本（还有 issue、PR、CI 流水线） |
| 换台电脑能用吗 | 不能，得重新构建 | 能，克隆下来就行 |
| 对方挂了会怎样 | 你本地跑不起来 | 代码还在本地，但 CI/CD 会挂 |
| 收费吗 | 个人版免费 | 公开仓库免费，私有仓库也免费 |

### 类比

- **Docker Desktop** = 你家的厨房。做饭（构建镜像）、吃饭（跑容器）都在这儿。
- **GitHub** = 云端保险箱 + 自动化工厂。菜谱（代码）放这里不会丢；你放进去一个新版本，工厂还会自动帮你做好菜打包（CI/CD 构建镜像）。

### 那为什么这个项目必须要 GitHub？

三条，按重要性排：

**① 你的代码现在只存在这一台电脑上。**

今天硬盘坏了，明天系统崩了，后天笔记本丢了——13577 行代码、70% 的工作量，**全没了**。Git 只是本地版本控制，它救不了"整台电脑没了"这种情况。传到 GitHub 才算真正有备份。

**② CI/CD 这个加分项，离开 GitHub 就没有载体。**

考核要求里"CI/CD 自动化"是加分项。这个自动化跑在哪？跑在 GitHub 的服务器上。你 `git push` → GitHub 的机器自动帮你构建镜像 → 推送到 GHCR → 服务器拉取更新。**没有 GitHub，这套流水线无处落脚**。

**③ Docker Desktop 没有任何备份和协作能力。**

它只管"跑"，不管"存"。你可以在本地构建出完美镜像，但：
- 换台电脑：一切从零重来
- 想分享：总不能把 788MB 的镜像发给评审老师
- 部署到腾讯云：服务器还是得从 GitHub 拉代码

### 一句话总结

> **Docker Desktop 负责"跑起来"，GitHub 负责"存下来 + 自动帮你跑"。前者是本地的厨房，后者是云端的保险箱兼流水线工厂。两个都要有，谁也替不了谁。**

### 那"云服务器"又是什么？三个东西，三个角色

你问"GitHub 是不是云服务器""腾讯云能不能代替 GitHub"——关键在于：**这三个东西干的是三件完全不同的事。**

| | Docker Desktop | GitHub / CNB / Gitee | 腾讯云服务器 |
|---|---|---|---|
| 它是什么 | 装在你笔记本上的**工具软件** | 云端的**代码托管 + 自动化平台** | 云端的**一台电脑** |
| 干什么 | 构建镜像、跑容器 | 存代码、自动构建、协作 | **7×24 小时开着跑你的网站** |
| 你能登进去吗 | 就在你本机 | ❌ 不能，它不给你机器 | ✅ 能，就是你的机器 |
| 关掉你的笔记本会怎样 | 网站停了 | **什么都不影响** | ✅ **继续对外服务**（这是"必须项1"的前提） |
| 收费 | 个人版免费 | 公开仓库免费 | 约 99–200 元/年起 |

> **GitHub 不是云服务器。** 它是"云端保险箱 + 自动化工厂"，但**它不给你一台机器去跑网站**。
>
> **腾讯云服务器也不能代替 GitHub。** 它代替的是**你笔记本在"跑网站"这件事上的角色**，而不是"存代码 + 自动构建"这件事。
>
> **一句话记忆法：GitHub 存代码，腾讯云跑网站，Docker Desktop 是你家的工作台。**

### 那"云服务器"能不能干 GitHub 的活？

技术上能（自己在那台机器上装 Git 服务 + Jenkins 也能跑流水线），但**不划算**：等于花 99 元买了台机器，只为了自己再搭一套 GitHub。别人做好的免费平台，没有理由不用。

**真正能代替 GitHub 的是"同一个物种"的平台**：Gitee（码云）、腾讯云的 **CNB（cnb.cool）**、阿里云效。它们和 GitHub 一样是**代码托管 + 流水线平台**。

### 选 GitHub 的理由 —— 不是"便宜"，是这四个

免费只是顺带的事。真正的理由按重要性排：

1. **异地备份**：你的代码现在只在这台笔记本上，硬盘坏了就全没了。**这是唯一无法替代的理由。**
2. **CI/CD 的载体**：那条自动构建流水线必须跑在某个云平台上，没有平台它无处落地（考核的加分项就没了）。
3. **部署的源头**：腾讯云上线时的流程是"从平台拉代码 → 构建 → 起来"。所以你**必须**有一个代码平台。
4. **业内标准 / 老师眼熟**：GitHub Actions 是评审最容易看懂的 CI/CD 方案，简历上写也更通用。

### 成本对比（2026-10 公开信息）

| 平台 | 免费额度 | 结论 |
|---|---|---|
| **GitHub** | 公开仓库 Actions **无限免费**；私有仓库 2000 分钟/月 | 足够用 |
| **CNB（腾讯云）** | 仓库存储 100 GiB + 对象存储 100 GiB + 构建 **160 核时/月** + 云端开发 1600 核时/月 | 也足够用 |
| **Gitee** | Gitee Go 有免费额度限制 | 够小项目用 |

**腾讯云服务器（必须项，S7 要用）参考价**：轻量应用服务器 2核2G4M 约 **99 元/年**（活动价），秒杀款更低。**大约一杯咖啡的钱，换一个能写进简历的线上作品——这是整个项目里性价比最高的一笔支出。**

### 具体怎么操作（注册 + 建仓库）

**第一步：注册账号**

1. 浏览器打开 `https://github.com/signup`
2. 填邮箱（建议用 `3215036573@qq.com`）、设密码（至少 8 位，含数字和小写字母）、起用户名（英文，比如 `chenjiale` 或 `jiale-dev`）
3. 邮箱会收到验证码，填进去
4. 完成人机验证，选免费版（Free）

**第二步：建一个空仓库**

1. 右上角 `+` → `New repository`
2. `Repository name` 填 **`my-tech-blog`**（或你喜欢的名字）
3. 下面三个选项**都不要勾**：
   - ❌ Add a README file
   - ❌ Add .gitignore
   - ❌ Choose a license
   （勾了会创建初始提交，和你本地的提交历史打架，得多一步处理）
4. 点 `Create repository`

**第三步：把仓库地址给我**

建完会显示一个地址，形如：

```
https://github.com/你的用户名/my-tech-blog.git
```

**把这个地址发给我**，我来做后续的关联和推送（包括配置好那条自动构建流水线），你不用敲命令。

> ⚠️ 提醒：推送时会弹一次登录窗口，需要你在浏览器里授权。到时候我会提前告诉你。

### 隐私提醒（重要）

推送到 GitHub 前，我会先确认三件事：

1. `.env` 文件（含数据库密码、JWT 密钥）**没有被提交** —— 已经在 `.gitignore` 里
2. 仓库设为 **Public（公开）** 或 **Private（私有）** 由你决定：
   - **Public**：评审老师能直接点进去看代码，**对考核更有利**
   - **Private**：更保险，但需要额外给老师开权限，反而麻烦
   - 建议：**Public**。代码里没有密码（密钥都在 `.env`，没提交），公开是安全的

## 七、GitHub 打不开 / 注册卡住怎么办（含国内替代平台）

### 第一步：别急着换平台，先排障（大概率 10 分钟内可解）

按顺序做，**做到哪一步通了就停**：

| 顺序 | 动作 | 判断标准 |
|---|---|---|
| 1 | **百度搜索「IP」**，看归属地（⚠️ 不要用 ipinfo.io，现在要登录） | 显示中国 → 代理没生效，做第 2 步；显示境外 → 直接跳到第 4 步 |
| 2 | 把代理软件从"**规则模式**"切成"**全局模式**" | 刷新 GitHub 页面，能不能出验证框 |
| 3 | **核对分流名单**：确认 `github.com`、`githubusercontent.com`、`githubassets.com` 都在代理名单里 | 验证框的图片/脚本来自后两个域名，漏一个就是"白框" |
| 4 | ⭐ **换节点**（换成日本 / 新加坡 / 美国，**尽量别用香港**） | 香港节点被 GitHub 限流很常见；换完刷新 |
| 5 | ⭐ **开 TUN 模式 + 远程 DNS（DNS over HTTPS）** | 治 DNS 污染。见下方"为什么 DNS 是重灾区" |
| 6 | 开一个**无痕窗口**（`Ctrl+Shift+N`）或换个浏览器 | 排除旧缓存和扩展干扰 |
| 7 | 用**手机热点 + 手机浏览器**试 | 移动网络出口 IP 通常更干净，这条路成功率意外地高 |
| 8 | 都失败 → **等 30 分钟到几小时**再试 | IP 信誉会冷却 |

> **注册入口别走错**：要直接在地址栏输入 `https://github.com/signup` 进入注册。**不要**从别的网站（比如 ipinfo）的"Sign in to GitHub"页面点进去——那是第三方网站用 GitHub 账号**登录**的入口，不是注册入口。

> **为什么第 3 步很关键**：人机验证的拼图、脚本来自 `github.githubassets.com` 这类**独立域名**。分流名单里只写了 `github.com` 时，页面能打开，但验证框永远是空白——**这就是"找不到验证图标"最典型的成因**。

### 为什么 DNS 是重灾区（2026-10-01 实测）

**一句话**：如果你的代理只接管了"网页请求"，却没接管"域名解析"，那么域名该指向哪个 IP 这个环节仍然走本地网络 → 结果可能是错的 IP → 表现就是"有的站能开、有的开不了、时好时坏"。

**实测到的铁证**：本机 DNS 是路由器地址（`192.168.1.1`），查 `www.google.com` 返回 **`31.13.92.37`** —— 那是 **Facebook 的 IP**。域名被指向了完全不相干的服务器，这就叫 **DNS 污染**。

**自查 DNS 有没有走代理**：换个节点或开远程 DNS 后，如果"时好时坏"的现象消失，说明之前就是 DNS 泄漏。

**查一个域名的真实 IP（加密 DNS，无法被篡改）**：浏览器打开
```
https://dns.google/resolve?name=github.com&type=A
```
返回的 `Answer` 里的 `data` 才是真实 IP。本项目实测 `github.com` 真实地址 `140.82.116.3`，而本机 DNS 给的是 `20.29.134.23` —— **两者不一致，就是污染的痕迹**。

### 第二步：如果确实修不好 —— 换国内平台，完全可行

实测各平台在当前网络环境下的可达性：

| 平台 | 实测结果 | 说明 |
|---|---|---|
| `github.com` | TCP 443 **可连通**，但 HTTPS 请求**超时**；`github.com/signup` 曾返回 **403** | 出口在中国香港，节点对 GitHub 链路不稳 |
| `gitee.com`（码云） | **200，直连也通** | 国内代码托管，**无需任何代理** |
| `cnb.cool`（腾讯） | **200** | 腾讯的代码托管平台，和腾讯云同生态 |

### 三个平台对考核的影响

| | GitHub | Gitee（码云） | CNB（腾讯） |
|---|---|---|---|
| 国内访问 | 需代理，不稳定 | **直连秒开** | **直连秒开** |
| 免费额度 | 公开仓库 Actions **无限免费**；私有 2000 分钟/月 | Gitee Go 有免费额度限制 | 仓库 100 GiB + 对象存储 100 GiB + 构建 160 核时/月 |
| 自带流水线 | GitHub Actions（**最标准、老师最眼熟**） | Gitee Go | 内置流水线（配置文件 `.cnb.yml`，语法和 Actions 类似） |
| 账号门槛 | 需邮箱 + 人机验证 | 手机号 | 支持**微信登录**、需实名认证 |
| 答辩演示 | 现场可能卡住 | **不卡** | **不卡** |
| 腾讯云服务器拉代码 | 慢、可能要配代理 | **快** | **快** |

### 我的建议（三层预案，别让这一步卡住主线）

> ⚠️ **最重要的一句话**：**CI/CD 只是加分项，而"公网可访问链接"是必须项。绝对不要为了 GitHub 卡住上线（S7）。**

1. **方案 A（首选）**：按上面第一步排障，通了就用 GitHub。理由：GitHub Actions 是评审老师最眼熟的 CI/CD 方案，简历上写也更通用
2. **方案 B（务实）**：用 **Gitee** 或**腾讯云 CNB（cnb.cool）**。CI/CD 用「**仓库 + WebHook → 腾讯云服务器上的部署脚本**」这套组合——你 `git push`，平台通知服务器，服务器自动 `git pull && docker compose up -d --build`。**演示效果和 GitHub Actions 一模一样（push 一下、网站自动更新），而且全程国内直连不卡。**
   - 选 **CNB** 的额外好处：支持**微信登录**、与腾讯云服务器同生态、免费额度大（构建 160 核时/月）
   - 选 **Gitee** 的额外好处：生态最接近 GitHub，用的人多、教程多
3. **方案 C（兜底）**：**先跳过 S6，直接做 S7 上线**（必须项优先），等上线跑通后再回来补 CI/CD

**另外提一句**：Gitee / CNB 和 GitHub **可以同时用**（一个本地仓库配多个远程地址，push 时都推）。将来如果 GitHub 通了，完全可以"GitHub 放公开代码给老师看 + 国内平台做快速部署"。
