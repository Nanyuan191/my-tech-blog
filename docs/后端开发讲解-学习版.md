## 二、我到底干了什么：16 个文件的职责

后端一共 16 个 TypeScript 文件。别看数量，每一个都有明确分工——**这就是"架构"，不是把代码堆在一个文件里就叫写完了**。

### 按层分类

```
apps/api/src/
├── server.ts          进程入口：只负责"监听端口"
├── app.ts             总装车间：装配中间件 + 挂载路由
├── config/
│   └── env.ts         环境变量集中管理（密钥、端口、数据库地址）
├── routes/            路由层：定义"哪些 URL 对应哪些处理函数"
│   ├── health.ts      健康检查
│   ├── auth.ts        登录/刷新/登出/改密码
│   ├── article.ts     文章相关（核心）
│   └── taxonomy.ts    分类 + 标签
├── middlewares/       中间件层：请求"过关卡"时做检查
│   ├── auth.ts        鉴权（三个关卡：必须登录/可选登录/角色校验）
│   └── errorHandler.ts 统一错误处理 + 异步包装器
├── controllers/       控制器层：校验入参 → 调服务 → 组装响应
│   ├── auth.controller.ts
│   └── article.controller.ts
├── services/          服务层：真正的业务规则 + 数据库操作
│   ├── user.service.ts
│   └── article.service.ts   （263 行，最核心）
├── lib/
│   └── prisma.ts      数据库客户端单例
└── utils/
    ├── auth.ts        JWT 签发/校验 + 密码哈希 + slug 生成
    └── logger.ts      分级日志
```

### 为什么分这么多层？（答辩会问）

一句话：**每一层只管一件事，改一处不会连带炸别的**。

| 层 | 只负责 | 不负责 |
|---|---|---|
| routes | URL 和数据类型的对应关系 | 业务逻辑 |
| middlewares | 进门前检查（登录了吗？有权限吗？） | 具体业务 |
| controllers | 校验参数格式、组装返回 JSON | 数据库操作 |
| services | 业务规则 + 读写数据库 | HTTP 相关的东西 |
| config | 读取环境变量 | 其他一切 |

**反例对比**：如果你把所有逻辑写在一个文件里，出现"文章列表返回的字段少了一个"这种问题，你得在大文件里翻找；而现在你直接去看 `article.service.ts` 的 `LIST_FIELDS` 就知道。

## 三、数据库：6 张表是怎么设计的

这是后端的"地基"。设计在 `apps/api/prisma/schema.prisma`，一份文件就是全部事实来源。

### 表关系图

```
User (用户)                 Category (分类)
  │ 1                          │ 1
  │                            │
  │ N                          │ N
Article (文章) ──── 1 : 1 ──┘
  │  │ N                      Tag (标签)
  │  └──[ArticleTag 中间表]──────┘ N    ← 文章和标签是"多对多"
  │ N
Comment (评论)  ← S8 附加功能要用
```

### 六张表各是什么

| 表名 | 干什么的 | 关键设计 |
|---|---|---|
| `users` | 存管理员账号 | 密码存 `password_hash`（bcrypt 加盐哈希），**绝不存明文** |
| `categories` | 文章分类（技术笔记/工程实践/随笔） | 一对多：一篇文章只属于一个分类 |
| `tags` | 文章标签（Vue/Docker/MySQL…） | 多对多：一篇文章多个标签，一个标签多篇文章 |
| `articles` | **核心表**，存文章 | 含标题、slug、摘要、Markdown 正文、状态、浏览量 |
| `article_tags` | 文章↔标签的中间表 | 复合主键，自带"同一篇不能重复打同一标签"的约束 |
| `comments` | 评论（S8 用） | 有审核状态，防垃圾评论 |

### 三个值得讲的细节

**① 文章状态用枚举，不用数字**

```prisma
enum ArticleStatus {
  DRAFT      // 草稿
  PUBLISHED  // 已发布
  ARCHIVED   // 已归档
}
```

对比：如果用 `0/1/2` 表示，三个月后你自己都不知道 `1` 是啥。枚举在数据库层就带上语义，也让前端下拉框可以直接用。

**② 加了复合索引**

```prisma
@@index([status, publishedAt])
```

列表页最常用的查询是"筛已发布的 + 按发布时间倒序"。没索引时数据库要一行行扫全表（几万篇时会明显变慢），加了索引就像给书加了目录，直接翻到要的位置。

**③ 外键带级联删除**

```prisma
article Article @relation(..., onDelete: Cascade)
```

删文章时，`article_tags` 里的关联记录会被数据库自动清理。**如果不写这行**，删完文章中间表会残留一堆指向"不存在的文章"的孤儿记录，越积越多。

## 四、一次请求的完整旅程（这段最值得看）

看懂这个，你就看懂了后端。

### 场景：访客打开一篇文章

```
① 浏览器请求    GET http://你的域名/api/posts/why-vue-express-over-nextjs
                        │
                        ▼
② Nginx 收到    /api 开头 → 转发给后端的 3000 端口
                        │
                        ▼
③ Express 流水线（app.ts 里按顺序排的）
     helmet        → 加安全响应头
     cors          → 仅开发环境（生产同域，不需要）
     compression   → 响应压缩
     json 解析     → 解析请求体
     cookieParser  → 解析 Cookie
     morgan        → 记一条访问日志
                        │
                        ▼
④ 路由匹配      routes/article.ts
                 先匹配固定路径 → 都不是 → 最后撞上 GET /:slug
                 ↑ 顺序错了就会 404，见"踩坑"一节
                        │
                        ▼
⑤ 鉴权关卡      optionalAuth
                 没带 token → 不报错，直接放行，req.user 为空
                 带了 token → 解析出来挂到 req.user
                        │
                        ▼
⑥ 控制器        article.controller.ts → detail()
                 isAdmin = req.user 存在且角色是 ADMIN/EDITOR
                        │
                        ▼
⑦ 服务层        article.service.ts → getArticleBySlug(slug, isAdmin)
                 · 查文章（连作者/分类/标签一起查）
                 · 文章不存在 → 抛 404
                 · 状态不是"已发布" 且 不是管理员 → 抛 404（防越权）
                 · 访客访问 → 浏览量 +1
                        │
                        ▼
⑧ 返回          { success: true, data: { ...文章 } }
                 ↑ 中文正文里的 Markdown 原样返回，渲染在前端做
```

### 关键设计点：为什么未发布的文章要返回 404 而不是 403？

这是个容易被追问的细节：

- 返回 **403 禁止访问** → 等于告诉攻击者"这篇文章**存在**，只是你没权限"
- 返回 **403 还是 404** 的差别，就是"泄露了信息"和"没泄露信息"的差别

所以我们统一返回"文章不存在"。攻击者无法通过状态码差异探测出你有哪些草稿。

### 场景：登录

```
POST /api/auth/login  { "username": "admin", "password": "<你的管理员密码>" }
        │
        ├─ Zod 校验参数格式（用户名非空、密码≥6位）
        ├─ user.service 查用户 + bcrypt 比对密码
        │    比对失败 → 401（不区分"用户不存在"和"密码错误"，同样是不泄露信息）
        ├─ 签发两个令牌：
        │    accessToken  → 放 JSON 里返回，前端存【内存】，2 小时有效
        │    refreshToken → 放 httpOnly Cookie，7 天有效，JS 读不到
        └─ 返回 { success: true, data: { accessToken, expiresIn, user } }
```

### 场景：发一篇文章

```
POST /api/posts   （带 Authorization: Bearer <accessToken>）
        │
        ├─ requireAuth 关卡 → 有令牌？是 access 类型？有效？→ 通过
        ├─ Zod 校验（标题非空、正文非空、状态只能是 DRAFT/PUBLISHED）
        ├─ service:
        │    · 由标题生成 slug（中文标题 → 退化为 post-随机串）
        │    · 摘要没填 → 自动截取正文前 150 字，去掉 Markdown 符号
        │    · status=PUBLISHED 才写 publishedAt，草稿留 null
        │    · 标签用嵌套 create 一次性写入（Prisma 自动包在一个事务里）
        └─ 201 + 文章数据
```

## 五、鉴权设计：三个关卡 + 两个令牌

### 三个中间件（`middlewares/auth.ts`）

| 中间件 | 什么时候用 | 没带令牌会怎样 |
|---|---|---|
| `requireAuth` | 后台接口、所有写操作 | **报 401 拦住** |
| `optionalAuth` | 文章详情（登录与否都能看，但看到的不一样） | **放行**，`req.user` 为 undefined |
| `requireRole('ADMIN')` | 需要特定角色时（当前预留） | 报 403 |

**为什么需要 `optionalAuth` 这个"中间态"？**

因为它让**一个接口同时服务前台和后台**：

- 同一个 `GET /api/posts/:slug`
- 匿名访客访问 → 只能看已发布文章
- 管理员带着令牌访问 → 能预览草稿（发布前先看看排版对不对）

如果用 `requireAuth`，访客就看不了文章了；如果用完全公开，管理员就预览不了草稿。`optionalAuth` 是这两者之间的第三条路。

### 两个令牌（为什么不用一个？）

| | accessToken | refreshToken |
|---|---|---|
| 有效期 | 2 小时 | 7 天 |
| 存放位置 | 前端**内存**（变量里） | httpOnly Cookie |
| 用途 | 业务请求时带上 | 只用来换新的 accessToken |
| 泄漏后果 | 最多 2 小时窗口期 | JS 读不到，XSS 偷不走 |

**答辩标准答法**：

> 如果只发一个长期令牌，一旦泄漏就等于永久失守，而且无法撤销。拆成两个之后，业务请求用的是短命的 accessToken，泄漏窗口被压缩到 2 小时；长期的那个放在 httpOnly Cookie 里，JavaScript 根本读不到，XSS 攻击也偷不走。
>
> 代价是：accessToken 存在前端内存里，所以**刷新页面就丢了**，需要靠 refreshToken 静默换一个新的。这是安全性和体验的折中——我选择把安全性放在前面。

⚠️ 注意这里有个你实测过的现象：**刷新 `/admin` 页面会被踢回登录页**。这不是 bug，是上述设计的必然结果，答辩时主动讲出来反而是加分项。

### 密码为什么不存明文（bcrypt）

```typescript
const SALT_ROUNDS = 10;   // 约 100ms 算一次哈希
```

- **哈希**：单向，从 `passwordHash` 反推不出原密码
- **加盐**：同一个密码每次生成的哈希都不一样（盐存在哈希字符串里），攻击者没法用"彩虹表"批量破解
- **cost=10**：正常登录感觉不到 100ms 的延迟，但暴力破解的成本被放大了约 1024 倍

## 六、我踩的坑（直接就是答辩素材）

这几条是真实发生的，不是我编的教学案例。**答辩时讲"我遇到什么问题、怎么解决的"，比背概念强十倍。**

### 坑 1：Express 路由顺序——固定路径被通配路径吃掉

`routes/article.ts` 里定义了 `GET /:slug`（按 slug 查文章）。同时还有 `GET /stats`（站点统计）。

**直觉写法**：`/:slug` 写在前面，因为它是"主要功能"。

**实际结果**：请求 `/api/posts/stats` 时，Express 会把它当成"查一篇 slug 等于 stats 的文章" → 返回 404。因为 Express 是**按注册顺序**匹配的，`:slug` 能吃掉任何单段路径。

**解法**：所有固定路径（`/stats`）和写操作（`POST`/`PUT`/`DELETE`）必须注册在 `/:slug` **之前**。详情接口放在最后，当"兜底"。

### 坑 2：Express 4 不会自动捕获 async 函数的错误

```typescript
router.get('/', async (req, res) => {
  throw new Error('炸了');   // ← Express 4 不管这个
});
```

**会发生什么**：错误变成"未处理的 Promise 拒绝"，请求**不会返回错误，而是直接挂起**，直到客户端超时。你看到的现象是"页面一直转圈"。

**解法**：写了一个 `wrap()` 包装器，把 async 函数包一层，手动把错误转交给 `next()`：

```typescript
export function wrap(fn) {
  return (req, res, next) => {
    void Promise.resolve(fn(req, res, next)).catch(next);
  };
}
```

用法：`publicRouter.get('/', wrap(articleController.list))`。这样所有异步错误都能被全局错误处理器接住。

### 坑 3：全局错误处理器必须正好 4 个参数

```typescript
export function errorHandler(err, req, res, next) { ... }
```

Express 靠**函数参数个数**来识别"这是错误处理中间件"。少写一个 `next`，它就被当成普通中间件，错误全部漏出去 → 返回给用户一个包含文件路径和库版本的完整堆栈。

**为什么危险**：堆栈信息会暴露你的项目结构、依赖版本，攻击者据此可以精准找已知漏洞。这是典型的"信息泄露"漏洞。

**我们的做法**：自定义错误处理器统一接管，规则是——**我们自己抛的业务错误**（如"文章不存在"）可以安全返回原文；**意外错误**只返回"服务器内部错误，请稍后重试"，完整堆栈只写进服务端日志。

### 坑 4：Prisma 的三个坑（详见 `docs/核心代码详解.md`）

1. 有 `prisma.config.ts` 时 CLI 不自动读 `.env` → 必须在首行 `import 'dotenv/config'`，否则报 `P1012`
2. `migrate dev` 需要影子库权限 → 开发环境要给数据库账号 `GRANT ALL`；生产用 `migrate deploy`
3. `jsonwebtoken` 库自己也导出一个叫 `JwtPayload` 的类型，和我们定义的冲突 → 我们的改名 `AuthPayload`，转换时走 `as unknown as`

## 八、答辩预演：后端部分可能被追问的问题

| 问题 | 一句话答法 |
|---|---|
| 为什么选 Express 不选 NestJS/Koa？ | 考核要求能讲清链路；Express 生态最成熟、中间件模型最直观，NestJS 的依赖注入对这个体量是过度设计 |
| 为什么用 Prisma 不写原生 SQL？ | 迁移有版本记录可回滚 + 编译期类型检查（字段写错当场报错）+ 防 SQL 注入 |
| 怎么防 SQL 注入？ | Prisma 全部走参数化查询，用户输入永远不拼进 SQL 字符串 |
| 怎么防 XSS？ | 前端 DOMPurify 清洗 Markdown 渲染结果；后端令牌放 httpOnly Cookie |
| 怎么防越权看草稿？ | 详情接口用 optionalAuth + 服务层判断状态，非发布一律返回 404（不泄露存在性） |
| 浏览量并发怎么保证不丢？ | 用 `increment: 1` 原子自增，不是"先读再写"（后者并发下会丢更新） |
| 分页为什么用 skip/take？ | 博客量级几百篇，offset 分页够用且能跳页；百万级才需要换成游标分页 |
| 列表接口为什么返回不含正文？ | 用 `select` 精确取字段而不是 `include`，正文几十 KB，一页 10 篇能省几百 KB |
| 响应格式为什么统一？ | 前端拦截器一套逻辑处理所有响应，不用每个接口单独写解析 |
| 用户注册接口为什么不开？ | 个人博客只有一个作者，管理员账号由 seed 脚本写入；开放注册等于给攻击者送入口 |
