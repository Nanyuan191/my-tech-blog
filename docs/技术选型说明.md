# 技术选型说明

> 考核「必须项2」的正式回答。
> 本文不只列技术栈，更说明**每个选择背后的约束和权衡** —— 选型的价值在于理由，不在于清单。

---

## 一、先说约束：选型不是自由的

技术选型必须先明确边界条件。这个项目有四条硬约束：

| # | 约束 | 来源 | 对选型的影响 |
|---|---|---|---|
| 1 | **必须能公网访问，且在国内稳定可达** | 考核必须项1 | 排除 `*.vercel.app` 等境外平台做主链接 |
| 2 | **必须包含 Docker 化部署** | 考核加分项1 | 排除 Serverless 平台（不运行 Dockerfile） |
| 3 | **必须能讲清前后端分工与鉴权** | 考核必须项3 | 排除纯静态生成器和 Git-based CMS（无后端无鉴权） |
| 4 | **单人开发，时间有限** | 现实条件 | 优先选生态成熟、文档丰富、AI 辅助友好的技术 |

**约束1和约束2的交集，是这次选型最关键的一步推理。**

大多数"个人博客"教程会推荐 Next.js + Vercel。它确实优雅，但在这两条约束下直接出局：

- Vercel 是 Serverless 平台，**不读 Dockerfile**。主站部署到 Vercel，那 `docker-compose.yml` 就只是个本地玩具，"一键拉起前后端及数据库"这句话无法自圆其说 → **违反约束2**
- `*.vercel.app` 域名在国内 DNS 解析不稳定（有解析到异常 IP、超时的实际报告）→ **威胁约束1**

所以必须选一条「自持服务器 + 容器编排」的路线。这是整套选型的起点。

## 三、逐项选型理由

### 3.1 前端为什么是 Vue 3 而不是 React

**决定因素：演示友好度。**

考核要求"讲清核心代码"，意味着我需要能一眼看懂自己的代码在干什么。

- Vue 的 `<script setup>` 把状态、计算属性、方法写在一起，**逻辑按功能聚合**；React 的 Hooks 有严格的调用规则（不能放条件里、依赖数组要手写），新手容易写出 bug
- Vue 的模板是 HTML 的超集，调试时可以直接在浏览器 DevTools 里看到组件树和响应式数据；React 的 JSX 在 DevTools 里是一层编译后的函数调用
- 响应式是 Vue 的核心卖点：改 `article.title` 视图自动更新，不需要 `setState` 再触发重渲染。心智负担更低

**其他考量：**

- **打包产物更小**：Vue 3 的运行时约 34KB（gzip），React 18 是 45KB 左右
- **中文资料密度**：Element Plus、Vite 的官方文档中文完整度高于同级 React 生态
- **不动摇的替代**：如果团队已经全是 React，那 React 是更优解 —— 技术选型要服从团队存量，只是这个项目里"团队"就是我一个人

**为什么用 Vite 而不是 Webpack：**

开发时 Vite **不打包**，浏览器直接以原生 ESM 方式按需加载模块。冷启动时间从 Webpack 的十几秒降到 **1 秒内**，热更新（HMR）同样是毫秒级。这在反复改样式的阶段体验差距极大。

生产构建时 Vite 换成 Rollup，产物比 Webpack 更小、tree-shaking 更彻底。所谓"开发快 + 生产小"，两者兼得。

### 3.2 前端为什么还要 Element Plus + Tailwind

**两个库职责不重叠，各管一块。**

| 库 | 负责 | 例子 |
|---|---|---|
| Element Plus | **交互组件**：表格、分页、对话框、表单校验、消息提示、上传 | 后台文章列表的表格、新建文章的弹窗 |
| Tailwind | **布局与间距**：flex、grid、padding、margin、响应式断点 | 首页的文章卡片网格、导航栏排版 |

**为什么不只用其中一个？**

- 只用 Tailwind：要手写表格的排序、分页、虚拟滚动，至少多花一周
- 只用 Element Plus：它的布局工具类很少，改一个间距要翻文档找类名，或者写一个 `.scoped` 的 style 块

**关于"用了组件库算不算自己写的"这个疑问：**

组件库解决的是**重复的、无技术含量的**部分。而本项目要展示的能力 —— **数据建模、鉴权设计、Markdown 安全渲染、容器编排、CI/CD** —— 一行都不会因此少写。用组件库是把时间投到真正需要思考的地方，这是工程判断，不是偷懒。

### 3.3 后端为什么是 Express 而不是 Nest.js / Fastify

**决策逻辑：Express 的"简单"在这个项目里是优势而非劣势。**

- **Nest.js** 提供依赖注入、装饰器路由、模块化架构，适合多人协作的大型项目。但对一个博客来说，它引入的抽象层（Module / Provider / Guard / Interceptor / Pipe）会让"讲清请求怎么走"变得困难 —— 我需要的是**能指着代码讲明白每一层在做什么**
- **Fastify** 性能比 Express 高（基准测试约 2-3 倍 QPS），但性能瓶颈在这个项目里根本不在于 Web 框架：**数据库查询和网络 IO 才是**。用 Fastify 换来的性能提升，用户感知不到；而它的插件生态和中间件数量都不如 Express 丰富
- **Express 的核心优势**：中间件模型直观（请求像水流过一串管道），生态最成熟，遇到问题搜索引擎命中率最高

**关于性能的客观说明：**

Express 4 在高并发下确实不如 Fastify。但本项目的实际负载是「个人博客」，QPS 峰值可能不到 10 —— 在这个量级下讨论框架性能差异属于过度优化。**如果这是电商秒杀系统，选型结论会完全不同** —— 技术选型必须匹配真实场景。

### 3.4 为什么必须是 TypeScript

**这是本项目贯穿始终的工程约束，不是可选项。**

```typescript
// 后端定义的数据结构
interface Article {
  id: number;
  title: string;
  slug: string;
  status: 'DRAFT' | 'PUBLISHED' | 'ARCHIVED';
}

// 前端直接复用同一份类型
import type { Article } from '@blog/api/src/types';
```

**带来的三个实际收益：**

1. **接口字段拼错会被编译器当场拦下**。把 `req.body.title` 写成 `req.body.tittle` → 编译不过。纯 JS 的话这个错误要等到线上运行、用户提交表单时才暴露
2. **重构有安全网**。给 `Article` 加一个必填字段，所有没处理它的地方会立刻标红，不会漏
3. **代码即文档**。看 `function createArticle(input: CreateArticleInput)` 就知道要传什么，不需要翻实现

**统一前后端类型的具体做法**：这个项目用 monorepo，前后端在一个仓库里，前端可以直接 `import type` 后端的类型定义，**不需要维护两份手抄的类型** —— 这是 monorepo 在这个场景下最实在的价值。

### 3.5 为什么是 Prisma 而不是原生 SQL / TypeORM

| 方案 | 优势 | 劣势 |
|---|---|---|
| 手写 SQL | 完全掌控，性能可精确优化 | 易注入（拼接字符串）、无类型、改表结构要手工同步 |
| TypeORM | 装饰器风格、社区大 | 类型推导较弱，复杂查询的返回类型常退化为 `any` |
| **Prisma** | **schema 为单一事实来源、类型完整、迁移有版本记录** | 生成的 SQL 偶尔不是最优（但可手写原生查询兜底） |

**选 Prisma 的三个决定性理由：**

**① schema 文件是单一事实来源**

```prisma
model Article {
  id          Int      @id @default(autoincrement())
  title       String   @db.VarChar(255)
  slug        String   @unique
  content     String   @db.Text
  status      ArticleStatus @default(DRAFT)
  publishedAt DateTime? @map("published_at")

  authorId    Int      @map("author_id")
  author      User     @relation(fields: [authorId], references: [id])

  tags        ArticleTag[]

  @@index([status, publishedAt])
  @@map("articles")
}
```

一个文件同时定义了：**表结构、字段类型、索引、外键、关联关系、迁移来源**。改这里，迁移 SQL 自动生成。数据库的现状和代码里的定义永远一致。

**② 迁移是带版本的文件，可以提交到 Git**

`prisma migrate dev` 生成 `migrations/20260930_init/migration.sql`。这意味着：

- 每张表的每次改动都有可追溯的 SQL 记录
- 部署到服务器时 `prisma migrate deploy` 会自动执行未应用的迁移
- 团队协作时不会出现"你改了表我不知道"的情况

**③ 生成的 Client 有完整类型提示**

```typescript
const articles = await prisma.article.findMany({
  where: { status: 'PUBLISHED' },
  select: { id: true, title: true },
});
// articles 的类型精确推导为 { id: number; title: string }[]
```

`where` 里写 `status: 'PUBLISHEDX'` → 编译报错（因为枚举里没有这个值）。表名写错、字段名写错，全部在编译期被拦下。

**关于"Prisma 生成的 SQL 不够优"这个批评**：确实存在。所以我在列表查询里用了 `select` 精确控制字段（不查 `content` 大文本），热点查询加了复合索引。**这是"知道工具的边界并主动补位"，而不是无脑信任 ORM**。

### 3.6 为什么是 MySQL 而不是 PostgreSQL

两者都是优秀的开源关系型数据库，本项目的需求两者都能完美满足。选 MySQL 的理由：

1. **国内云厂商的默认与主流**。腾讯云、阿里云的数据库产品文档、监控、备份工具对 MySQL 的支持最完善，服务器上一句 `apt install mysql-server` 就能用
2. **运维资料密度**。遇到问题搜索时，中文 MySQL 解决方案的数量明显多于 PostgreSQL
3. **考核场景的适配**。这是博客，不需要 PostgreSQL 的地理空间索引、数组类型、JSONB 高级查询等特有能力

**为什么锁定 8.0 版本：**

- **`utf8mb4` 字符集**：8.0 默认就是 utf8mb4，能正确存储 emoji 和生僻字。5.7 默认 `utf8` 实际是 3 字节，存 emoji 会报错或丢字符 —— 这个坑很经典
- **窗口函数**：`ROW_NUMBER()`、`RANK()` 等，做排行榜类需求时不用写复杂的自连接
- **JSON 原生类型**：如果以后要给文章加可扩展的元数据字段，`JSON` 列类型比 5.7 的 JSON 支持完善得多

**docker-compose 里的配套设置：**

```yaml
command:
  - --character-set-server=utf8mb4
  - --collation-server=utf8mb4_unicode_ci
  # 8.0 默认认证插件是 caching_sha2_password，
  # 部分老客户端连不上，改成 mysql_native_password 兼容性更好
  - --default-authentication-plugin=mysql_native_password
```

### 3.7 为什么鉴权用 JWT + bcrypt

**密码存储：bcrypt，绝不存明文。**

```typescript
const SALT_ROUNDS = 10;   // cost factor
const hash = await bcrypt.hash(plainPassword, SALT_ROUNDS);
```

- **自带盐值**：同一密码每次哈希结果都不同，攻击者无法用彩虹表批量比对
- **可调成本因子**：cost=10 意味着 2^10 = 1024 轮迭代，一次哈希约 100ms。对正常登录无感，但把暴力破解的成本放大了 1024 倍
- **专为密码设计**：相比 SHA-256 这类"快哈希"，bcrypt 故意设计得慢 —— 这正是密码存储需要的特性

**令牌：access + refresh 双令牌。**

| 令牌 | 有效期 | 存储位置 | 用途 |
|---|---|---|---|
| access token | 2 小时 | 前端内存变量 | 访问所有接口 |
| refresh token | 7 天 | `httpOnly` Cookie | 仅用于换新 access token |

**设计动机：单令牌方案有两个死结。**

- 只用一个长期 token → 一旦泄漏等于永久失守，且无法撤销
- 只用一个短期 token → 用户每隔几十分钟就被踢出登录

拆成两个之后：access 泄漏的窗口只有 2 小时；refresh 因为存在 `httpOnly` Cookie 里，**JavaScript 读不到**，所以即使发生 XSS 也偷不走它。

**access token 为什么不放 `localStorage`？** 因为 `localStorage` 能被 JS 读取，XSS 一旦成功就能直接把 token 发到攻击者服务器。放内存变量里，刷新页面就没了（由 refresh 流程恢复），但 XSS 拿不到。

**关键安全细节**：两个令牌用**同一个密钥**签名，所以必须用 `type` 字段区分用途，否则 refresh token 可以直接当 access token 用：

```typescript
if (payload.type !== 'access') {
  throw AppError.unauthorized('令牌类型不正确');
}
```

### 3.8 为什么用 Nginx 而不是 Node 直接托管前端

**两个必须由 Nginx 解决的问题：**

**① SPA history 路由回退**

Vue Router 用 history 模式时 URL 是真实路径。在 `/posts/xxx` 刷新页面，浏览器会真的请求这个路径 —— 而服务器上并没有这个文件，直接 404。

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

**② 反向代理让前后端同源**

```nginx
location /api/ {
    proxy_pass http://api:3000;
}
```

浏览器看到的所有请求都来自同一个域名和端口，**跨域问题从根上消失**。同时生产环境只需要暴露一个端口。

**为什么 Node 不适合托管静态文件：**

- 静态文件服务是 IO 密集型的，Node 单线程模型下会成为瓶颈
- Nginx 用 `sendfile` 系统调用（零拷贝）直接在内核态把文件送到网卡，不经过用户态内存拷贝，性能高一个量级
- Nginx 原生支持 gzip、强缓存头、限流，这些都是几行配置的事

**顺带说一个容易忽略的性能细节**：带 hash 的构建产物可以放心地强缓存一年：

```nginx
location ~* \.(js|css|woff2?|png|jpe?g|webp)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

因为 Vite 生成的文件名里带了内容 hash（如 `index-a1b2c3.js`），**内容变了文件名就变**，所以永远不会加载到过期内容。而 `index.html` 必须设成不缓存，否则发新版本后用户还在加载旧的资源清单。

### 3.9 为什么用 GitHub Actions + GHCR

**为什么是 Actions 而不是 Jenkins / GitLab CI：**

- 代码已经在 GitHub 上，Actions **零额外基础设施**（不用自己搭一台 CI 服务器）
- 公开仓库的 Actions 完全免费
- 工作流就是仓库里的一个 YAML 文件，改动有 Git 记录

**为什么镜像推 GHCR 而不是 Docker Hub：**

| 对比项 | GHCR | Docker Hub |
|---|---|---|
| 鉴权 | 用仓库自带的 `GITHUB_TOKEN`，**零配置** | 需要在 Secrets 里额外配账号密码 |
| 国内访问 | 相对稳定 | 时有超时 |
| 私有镜像 | 免费 | 免费额度有限（1 个） |

**"密钥越少，泄漏面越小"** —— GHCR 不需要在 Secrets 里存 Docker Hub 的凭据，少一个泄漏点。

**流水线设计要点：**

```yaml
build-and-push:
  needs: lint          # ← 快速失败：lint 不过就不构建
```

类型检查不通过说明代码有问题，没必要浪费时间和 Actions 额度去构建镜像。

**部署末尾必须清理旧镜像：**

```bash
docker image prune -f
```

每推一次代码就多一个镜像标签，不清的话服务器磁盘很快被撑满 —— 这是最容易忽略但**一定会出问题**的一点。

### 3.10 为什么选腾讯云轻量应用服务器

**部署方案的核心决策：主链接用 `http://<公网IP>:8080`，而不是域名。**

**原因是 ICP 备案这个硬约束：**

> 在中国大陆节点上，**80 和 443 端口必须完成 ICP 备案**才能对外提供服务（备案周期 3-20 个工作日）。备案未通过前，绑定域名访问会被运营商拦截。

**所以分两步走：**

| 阶段 | 访问方式 | 前提 |
|---|---|---|
| **交付期（立即）** | `http://<公网IP>:8080` | 无 —— 非标准端口不受备案限制，**开通当天即可用** |
| **长期（备案后）** | `https://域名` | 需完成 ICP 备案 |

这样做的价值是：**必须项1「线上可访问链接」完全不依赖备案进度**，不会因为备案卡住而失去分数。备案同步启动，通过后再平滑切换。

**为什么是腾讯云而不是阿里云 / 华为云：**

三家产品力和价格接近，选腾讯云是基于：

- 轻量应用服务器（2核2G）约 60 元/月的档位足够跑三个容器
- 控制台对新手友好，防火墙规则（安全组）配置直观
- 学生认证有优惠

**为什么是"轻量应用服务器"而不是 CVM（云服务器）：**

轻量的定位就是"开箱即用"，默认给公网 IP、默认配好基础安全组，不需要像 CVM 那样自己配 VPC、子网、弹性 IP。**对单人项目来说，少一层网络抽象就少一类故障。**

**服务器侧的安全设计：**

```yaml
services:
  db:
    # 不写 ports —— 数据库不暴露到公网
  api:
    # 不写 ports —— 只有 web 能访问它
  web:
    ports:
      - "8080:80"   # 唯一对外入口
```

这就是**最小暴露面原则**。三个容器在同一个 bridge 网络里，用服务名互相寻址（后端连库是 `db:3306` 而不是 `localhost:3306`），外部完全访问不到 `api` 和 `db`。

**如果不这样做会怎样**：把 MySQL 的 3306 暴露到公网，在网上扫描器无差别扫描的背景下，只要密码强度不够，数据被拖走是迟早的事。

## 四、明确排除的方案（以及为什么）

> 记录这些是为了说明选型经过比较，而不是拍脑袋。

### 4.1 Next.js 14 + Vercel + PostgreSQL + Auth.js

**评估过程**：这是目前个人博客最流行的方案，生态成熟、开发体验好。

**否决理由（两条独立的致命问题）**：

**① Docker 加分项无法成立**

Vercel 是 Serverless 平台，**构建流程里没有容器环节，不会读 `Dockerfile`**。这意味着：

- `docker-compose.yml` 只能在本地跑，线上用不上，变成"演示道具"而非真实部署方案
- 线上数据库（Neon）和本地容器的 PostgreSQL 是两套环境，违背了"容器化保证环境一致"的初衷
- **"一条命令拉起前后端及数据库"这句话讲不圆** → 直接损失加分项1

**② 威胁必须项1**

`*.vercel.app` 域名在国内 DNS 解析不稳定，配合 Neon / Supabase 同属境外服务，存在访问超时风险。而"公网可访问"是必须项，不能赌。

**③ 附带问题**：Vercel 的免费额度有冷启动，长时间无访问后首次打开要等几秒 —— 演示时体验不佳。

**结论**：这个方案在"开发体验"上更优，但**不满足本项目的硬约束**。选型必须服从约束，不能因为方案流行就套用。

### 4.2 Astro / VitePress 纯静态 + GitHub Pages

**评估过程**：用 SSG 生成纯静态站，推到 GitHub Pages 托管，完全免费。

**否决理由**：

| 考核项 | 能否满足 | 原因 |
|---|---|---|
| 必须项1 线上链接 | ✅ | GitHub Pages 可用（但国内访问速度一般） |
| 必须项2 技术栈说明 | ✅ | 有内容可讲 |
| 必须项3 核心代码详解 | ❌ | **没有后端、没有鉴权、没有数据库**，题目明确要求"后台发布/鉴权" |
| 加分项1 Docker 化 | ❌ | 静态站不需要容器，编排无从谈起 |
| 加分项2 CI/CD | ⚠️ | 只能做简单的 Pages 部署，含金量低 |

**核心否决点**：题目原文要求"实现一个包含前端展示与**后端管理**的个人技术博客系统"，且必须项3明确列出"**后台发布/鉴权**"。纯静态方案等于放弃一半必须项。

### 4.3 可吸收的部分

虽然没有采用上述方案，但评估过程中摘取了一些做法：

- **Tailwind CSS**：Vue 同样支持，本项目中已采用
- **GitHub Actions 的影子站 job**：主链接在腾讯云，但可以加一个 job 把静态快照推到 GitHub Pages 作为**备份演示链接** —— 万一服务器出状况，还有备用入口

## 五、技术选型对照表（速查）

| 决策点 | 选择 | 一句话理由 |
|---|---|---|
| 前端框架 | Vue 3 | 逻辑聚合、调试直观、中文资料密度高 |

| CI/CD | GitHub Actions + GHCR | 零基础设施，密钥管理最简 |
| 部署 | 腾讯云 + IP:8080 | 零备案依赖，当天可交付 |
